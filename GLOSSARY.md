# Glossary

**Universe** — the set of files an analysis considers: a regular file tracked by git (no symlink or submodule), not ignored, not marked `linguist-generated` or `linguist-vendored`, not below `vendor`, `node_modules`, `dist`, `build`, `generated`, `__generated__`, or `tsp-output`, not binary or minified, and matching the language allow-list, the contract list, or the `--include` globs (which replace both lists; a file that names a contract stays a contract). Scores and coupling are relative to the universe. Its files are **code files**, which are scored, and **contract files**, which only couple.

**Contract file** — an interface definition or schema whose changes drive changes in code: a file with the extension `.tsp`, `.proto`, `.graphql`, `.gql`, `.avsc`, `.thrift`, or `.smithy`, a JSON Schema (`*.schema.json`), or an OpenAPI, AsyncAPI, or Swagger description by name (`openapi.*`, `asyncapi.*`, `swagger.*` in YAML or JSON). A contract file is in the universe by default (`--exclude` removes it), takes part in coupling (`Coupling.kinds`, `Partner.kind`), and counts as a touch of the module it lives in, the nearest module above it (the root module houses only contracts at the top of the repository) or else the highest directory above it that holds no code, which makes no module (a module partner like that is `contractsOnly`), for cohesion and partners. A commit that touched only contract files counts in `window.commits` and `couplingCommits`. Couplings with a code side are listed before pairs of two contract files, which the terminal's coupling table leaves out like test pairs. It has no score, rank, or complexity, is never listed in `files`, and counts for no module's size, entry points, leakage, or depth; `Report.contracts` lists it with its revisions and lines. Its import relation is unknown (`null`). The output generated from a contract (`tsp-output/`, `generated/`, `__generated__/`) is not in the universe: contract and generated code are linked through coupling, not through a generator model.

**Ubiquitous file** — a contract file that changed in more than 30 % of the counted commits and in at least 10 of them (`thresholds.ubiquitousShare`, `ubiquitousMinCommits`), judged per window. A central schema that every change touches would couple to everything, so it is listed in `Report.ubiquitousFiles` and left out of every coupling pair, breadth, and module cohesion; it stays in `Report.contracts`.

**Focus** — the files a question is about (`inspect <file-or-glob...>`). Focus narrows what is reported, never the universe.

**Analysis window** — the time range of history considered (`--since`, default 12 months), resolved to absolute dates in the report.

**Revisions** — the number of non-merge commits in the analysis window that touched a file, following renames. A path deleted and created again with other content starts afresh: a file's revisions do not include a deleted file that once had its name, as far as non-merge commits show it; one that comes back with the very content it had (a revert, a re-land) is the same file and continues. Deletions and creations made only inside merge commits are not seen, so a path recreated after a deletion made only inside a merge inherits the old history. The churn signal. A shallow clone lacks the history before its oldest commit, so its revisions undercount.

**Indentation complexity** — the sum of logical indentation levels over a file's non-blank lines. A language-agnostic proxy for structural complexity.

**Weighted lines** — a file's size as the score sees it: every non-blank line counts 1 plus its indentation level, so flat files (barrels) keep their weight and nesting adds to it.

**Hotspot** — a file that is both large or complex and frequently changed. Its **score** (0..1) is the product of its log-max-normalized revisions and weighted lines.

**Change coupling** — two files that repeatedly change in the same commits. Coupling across distant directories signals a missing or misplaced module boundary.

**Coupling degree** — `shared commits / mean(revisions of both files)`, 0..1. Symmetric; ranks coupled pairs.

**Co-change probability** — `shared commits / revisions of one file of the pair`. Directional: how likely a change to that file also changes the other. `inspect` shows it for the focused file, `analyze` for both files of a pair.

**Test pair** — a coupled pair where one file is the other's test (`Coupling.testPair`). The test has a suffix (`.test`, `.spec`, `_test`, `_spec`) and either sits beside its source (`a.ts` and `a.test.ts`) or lies below a **mirrored test directory** (`test`, `tests`, `__tests__`, `spec`, `specs`, `e2e`) whose mirror holds the source: the same path with that directory removed or replaced by `src` or `lib` (`src/a/b.ts` and `test/a/b.test.ts`, `lib/x.ts` and `__tests__/x.test.ts`, `packages/p/src/y.ts` and `packages/p/test/y.test.ts`, `src/x.ts` and `src/__tests__/x.test.ts`). A file below a test directory without a suffix (a helper, a step file such as `login.steps.ts`, a mock) and anything below a `fixtures` or `__fixtures__` directory, suffix or not, is test code but nobody's test, and no fuzzy name matching pairs files elsewhere in the tree. Expected coupling, never a modularization smell.

**Co-change breadth** — the number of distinct other universe files (contract files included, ubiquitous ones not) a file changed together with in counted commits (at most `maxCommitFiles` files each), however rarely. A **hub** is a hub candidate (at least `hubMinRevisions` revisions, not test code) whose breadth is at least `hubMinBreadth` and among the widest `hubTopShare` of the candidates, ties at the cut-off included; it is explained with a reason line, even when no single pair is coupled strongly enough to report.

**Module** — the unit the report groups universe files into. A **package** is a directory, other than the repository root, with a tracked manifest (tracked is enough: an ignore rule that matches it does not matter; `package.json`, `go.mod`, `Cargo.toml`, `pyproject.toml`, `pom.xml`, `build.gradle`, `build.gradle.kts`, or `*.csproj`); a file belongs to its nearest enclosing package. Files outside every package form **directory** modules, cut at the first depth where they split into at least two directories (at the first level when no depth does); root files form `.`. When that leaves fewer than two modules, all files are regrouped by directory. A module that holds more than 70 % of the universe files, and at least 20, is **dominant**: its files are split by the same directory rule, again while a part is dominant, until none is or no directory splits the last one (a module that big has nearly every commit inside it, so its cohesion says nothing; a smaller one is left alone). A package is split only when no other package with files in the analysis exists (a package of test code alone, such as a fixture's manifest, does not count): the largest of several packages is a boundary someone declared and stays one module, however large. A split package becomes directory modules but stays importable by its name, and its manifest still names entry points, which fall to the piece that holds them; usually that is the entry file alone, a module of its own, so the leakage and depth of the split code come out `null`. Beyond the 20-file floor for a dominant module there is no size floor: every package among others is a module.

**Cohesion** — of a module, `commits touching only this module / commits touching it`, over counted commits (a commit that touched a contract file housed in the module touched the module; a contract file outside every module counts as another place); `null` without counted commits. Its **partners** are the other modules those commits touched, most shared commits first. A coupling that **crosses a module** joins files of different modules; that is stated neutrally, since an app legitimately changes with the library it uses. A module is **ranked** when it has at least `minModuleCommits` counted commits (`max(5, ceil(1% × couplingCommits))`) and is not **test-only**; the report, terminal, and viewer list ranked modules first, least cohesive first.

**Test code** — a file whose name has a test suffix (`.test`, `.spec`, `_test`, `_spec`) or that lies below a directory named `test`, `tests`, `__tests__`, `spec`, `specs`, `e2e`, `fixtures`, or `__fixtures__`. A **test-only module** (`Module.testOnly`) consists of test code alone. Never ranked: its cohesion says nothing about the design.

**Entry point** — a file that makes up a module's public interface. For a package: the files its `package.json` names in `exports`, `main`, `module`, or `types`, counting only JavaScript and TypeScript files and no `*.config.*` files (a `*` in a target matches any files, a target without extension finds the file with that name, and a `dist/` or `build/` target stands for the same-stem source under the module when one exists) and the conventional `index.{ts,tsx,mts,cts,js,jsx,mjs,cjs}`, `mod.rs`, `lib.rs`, `__init__.py` at the module root or its `src/`; for a directory module only the conventional files, plus, for a piece of a split package, the manifest-named files that lie in it. `--entry <glob>` replaces detection. Its **interface commits** are the counted commits that touched an entry point; its **implementation commits** those that touched any other file of the module that is not test code.

**Leakage** — of a module, `implementation commits that also touched an entry point / implementation commits`, 0..1; `null` without entry points or implementation commits. High leakage means changes inside the module keep changing its public API (a shallow or leaky module). A module is a **leaky interface** (`Module.leakyInterface`) when it is not test-only and its leakage is at least `minLeakage` over at least `minImplementationCommits` implementation commits; its entry points that changed in a commit that also changed the implementation get a reason. Unlike the cohesion ranking, that commit floor does not grow with the window: it only keeps a share of a handful of commits from counting. Low leakage behind an `export *` barrel does not prove a stable API, and an entry file that holds most of a module's code inflates leakage.

**Comparison window** — with `--compare <duration>`, the window of the same length that ends where the analysis window starts. Both are read in one pass over the history and measured over the same universe, with the same fixed limits (such as `maxCommitFiles`); `minModuleCommits` is derived per window, and the report's thresholds are the analysis window's. The report describes the analysis window, the comparison window only feeds the trends. The comparison window is **truncated** when it reaches back past the oldest commit of the repository or of a shallow clone, and **empty** (`previousCommits` 0) when no commit touched the universe in it: there is then nothing to compare.

**Trend** — how a file or module moved between the comparison window and the analysis window. A file's **score delta** is its score now minus its score then, each normalized within its own window, so it shows a shift in standing among the files rather than a change in raw revisions; a module's **cohesion delta** is the change in its cohesion, positive when it became more self-contained. A file with no revisions in the comparison window but some now is **newly active** (`trend.newlyActive`): its score delta is just its score, so it is never ranked as warming. A file deleted and recreated at the same path is judged by the file that exists today in both windows, never by its predecessor. A module's trend needs at least `minModuleCommits` counted commits in both windows. A trend is `null` without `--compare`, and where a window has no data to compare. The treemap draws it as _cooler_ (score fell) to _warmer_ (score rose).

**Import relation** — of a coupled pair, whether a static import links the two files: `Coupling.imports` is `a→b` when `a` imports `b`, `b→a`, `both`, or `none`; `null` when it is unknown. A file imports another when it names it in a static `import`, `export … from`, a dynamic `import()` with a plain string, a `require()`, the `import("…")` of a TypeScript type, or `new URL("./x", import.meta.url)`, or imports a module that hands it on (transitively): one that re-exports it with `export … from`, or has the import, or the `require()` call, inside an exported expression (the initializer of an exported variable, `export default <expression>`, `export { name }`, `export =`, `module.exports = …`, `exports.x = …`; a name stands for what its variable was initialized with and assigned, through any number of top-level names). Only a name that references the import counts (not a plain property key, a member after the dot, or a JSX attribute name), and not one used inside a function or class within that expression: `export const api = { go: () => run() }` does not hand on `run`, while a `require()`, `import()`, or `new URL(…, import.meta.url)` does wherever it is (an exported `() => import("./page")` hands on `./page`), and so do what a class extends and what its decorators name, which are evaluated with the class (an `implements` clause is a type reference and does not hand on). Functions are hoisted, and `Object.assign(module.exports, require("./t"))` and tsc's `__exportStar(require("./t"), exports)` put what they are given on the exports. A top-level name stands for the modules its own initializer loads or refers to, plus what is assigned to it or to a member of it at the top level (also inside `if` and `try`, never inside a function: `Form.Item = Item`, `impl = require("./t")`), so exporting `const helper = require("./h").helper` hands on `./h`. An exported `import X = …` and an exported type alias that names an imported type hand on too; an interface that extends one does not. Relative specifiers, workspace package names (the files their manifest maps `"."` to, among the files the package owns, or, for a package that owns none such as a folder above its sub-packages, among all files below it, unless a package that owns files claims the same name), and nothing else resolve to universe files. The relation is **unknown** (`null`) when a file is not TypeScript or JavaScript, does not parse, or lies behind an unavailable parser, and when no import links the pair but some module involved is not **accounted for**: the two files, every file they import, and every file those hand on through must be readable and, where they are parsed, load only universe files, Node built-ins (a bare name that a directory, or a code file without its code extension, of the repository also carries is not one), packages some manifest declares (or its `@types`), workspace packages, and tracked assets. A tsconfig `paths` alias, a `#` subpath import, a bundler plugin scheme, an undeclared package or one whose name two manifests claim, code outside the universe, a component file (`.vue`, `.svelte`, `.astro`), or modules loaded by an expression (`import(name)`, `import.meta.glob()`, `require.context()`) makes it unknown. In an `inspect` partner the same relation is seen from the inspected file (`file→partner`, `partner→file`).

**Hidden coupling** — a coupled pair whose import relation is `none`: the files change together without referring to each other, so the shared contract (duplicated logic, a protocol, configuration read twice) is invisible in the code. A file whose strongest non-test partner is hidden with a co-change probability of at least `minHiddenProbability` (0.5) gets a reason line. Test pairs are never called hidden.

**Copy family** — a connected group of files with largely the same content that keep changing in the same commits (`Report.copyFamilies`, `InspectResult` `copyFamily`): the same change applied to each copy. Among the coupled pairs that are no test pair, two files are **similar** when the **Jaccard index** of their sets of **shingles** is at least `minCopySimilarity` (0.5); a shingle is a run of five consecutive words of the file as the tokenizer reads it: identifiers and keywords as they are, every string literal and number as one placeholder, no whitespace, punctuation, or comments (`//`, `/* */`, `<!-- -->`, `#` at the start of a line); a file with fewer than 20 distinct shingles is too small to compare. A family reports its sorted `files`, the `similarity` range (`min`, `max`) over all pairs of its members (the weakest can lie below the threshold: A like B and B like C make a family although A and C share little), `sharedChanges` (counted commits that touched at least two members), and `changesToAll` (counted commits that touched every member: the fixes applied to all copies). A family is `testOnly` when every member is test code; those rank after the others and stay out of the terminal's list. It says the files change in lockstep, never that anything is wrong: one adapter per entity or one config per environment is duplication on purpose.

**Language adapter** — the engine's seam to a language: one small adapter per language, selected by file extension, that lists what a file imports and what it exports. Only the TypeScript and JavaScript adapter exists; the CLI injects its parser (`oxc-parser`), so the engine depends on no parser.

**Depth** — of a module (`Module.depth`), how much implementation sits behind how much interface: `{ exports, implementationLines, linesPerExport }`. `exports` is the number of distinct names its entry points export (a name that several entry points export counts once), following `export * from` within the module (as in ECMAScript: the file's own export wins, `default` is not forwarded, and a name that two `export *` sources export as different bindings is exported by neither), `export { x } from`, and `export * as ns from`; `implementationLines` is the `loc` of its files that are neither entry points, test code, nor tool configuration (`*.config.*`); `linesPerExport` is their quotient. A **deep module** has few exports over much implementation (many lines per export), a **shallow module** a wide interface with little behind it (few lines per export). The terminal lists the shallowest ranked modules. Depth is `null` where it cannot be told exactly (see `Module.depth`), never zero; it describes the code as it is now, not the window.
