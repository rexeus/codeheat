# Glossary

**Universe** — the set of files an analysis considers: a regular file tracked by git (no symlink or submodule), not ignored, not marked `linguist-generated` or `linguist-vendored`, not below `vendor`, `node_modules`, `dist`, `build`, `generated`, `__generated__`, or `tsp-output`, not binary or minified, and matching the language allow-list, the contract list, or the `--include` globs (which replace both lists; a file that names a contract stays a contract). Scores and coupling are relative to the universe. Its files are **code files**, which are scored, and **contract files**, which only couple.

**Contract file** — an interface definition or schema whose changes drive changes in code: a file with the extension `.tsp`, `.proto`, `.graphql`, `.gql`, `.avsc`, `.thrift`, or `.smithy`, a JSON Schema (`*.schema.json`), or an OpenAPI, AsyncAPI, or Swagger description by name (`openapi.*`, `asyncapi.*`, `swagger.*` in YAML or JSON). A contract file is in the universe by default (`--exclude` removes it), takes part in coupling (`Coupling.kinds`, `Partner.kind`), and counts as a touch of the module it lives in, the nearest module above it (the root module houses only contracts at the top of the repository) or else the highest directory above it that holds no code, which makes no module (a module partner like that is `contractsOnly`), for cohesion and partners. A commit that touched only contract files counts in `window.commits` and `couplingCommits`. Couplings with a code side are listed before pairs of two contract files, which the terminal's coupling table leaves out like test pairs. It has no score, rank, or complexity, is never listed in `files`, and counts for no module's size, entry points, leakage, or depth; `Report.contracts` lists it with its revisions and lines. Its import relation is unknown (`null`). The output generated from a contract (`tsp-output/`, `generated/`, `__generated__/`) is not in the universe: contract and generated code are linked through coupling, not through a generator model.

**Ubiquitous file** — a contract file that changed in more than 30 % of the counted changes and in at least 10 of them (`thresholds.ubiquitousShare`, `ubiquitousMinCommits`), judged per window. A central schema that every change touches would couple to everything, so it is listed in `Report.ubiquitousFiles` and left out of every coupling pair, breadth, and module cohesion; it stays in `Report.contracts`.

**Focus** — the files a question is about (`inspect <file-or-glob...>`). Focus narrows what is reported, never the universe.

**Analysis window** — the time range of history considered (`--since`, default 12 months), resolved to absolute dates in the report.

**Revisions** — the number of non-merge commits in the analysis window that touched a file, following renames, leaving out mechanical commits. A path deleted and created again with other content starts afresh: a file's revisions do not include a deleted file that once had its name, as far as non-merge commits show it; one that comes back with the very content it had (a revert, a re-land) is the same file and continues. Deletions and creations made only inside merge commits are not seen, so a path recreated after a deletion made only inside a merge inherits the old history. The churn signal. A shallow clone lacks the history before its oldest commit, so its revisions undercount.

**Mechanical commit** — a commit in the window that, as far as git can tell, changes the repository without changing what its code does, so it is no revision, no churn, and no coupling, cohesion, or interface-churn evidence; it still counts in `window.commits` and carries renames forward. Its **kind** (`Report.mechanicalCommits` counts each) is the first that applies: `ignored` (listed in `.git-blame-ignore-revs` at `HEAD`), `renames` (every change is an exact rename or a mode change), `whitespace` (the diff is empty under `git diff -w`, and no file of the commit belongs to a language where indentation is syntax, such as Python, Starlark/Bazel, F#, Haskell, Scala, YAML, or a Makefile), `reverts` (a commit that says `This reverts commit <sha>` together with that commit, when both are in the window and the revert undoes the original exactly over the analyzed files, that is the code and contract files of the universe (same paths, mirrored line counts, and each file confirmed undone: restored to the object it had before the original, or the revert's patch for it equals the original's reversed, context and position not compared; a change of type never confirms; files outside the universe, such as lockfiles, neither break nor make a pair): a revert of a commit outside the window counts normally), `duplicates` (the patch id, `git patch-id --stable`, equals an older commit's in the window and the older commit is not an ancestor: a cherry-pick or backport on a parallel line; the oldest counts; a **re-land**, the same patch applied again on top of the older commit after a back-out, is a real change). Pairs and duplicates are found inside one window. Whitespace is `git diff -w`, so a change that only adds a space inside a string literal counts as whitespace (a known limit: `-b` would stop catching formatter runs that insert spaces).

**Logical change** — the unit that coupling, module cohesion, interface churn, breadth, and copy families count (`Report.logicalChanges`): one commit, or the real commits that belong together. Commits belong together when they share a pull request, which is the same `(#123)` at the end of a squash-merge subject (within 14 days of the first of them), or a merge commit whose message names a pull or merge request (GitHub, Bitbucket Cloud and Server, GitLab, and Azure DevOps formats) that brought them in (the innermost one for a branch merged into another branch, each branch of an octopus merge on its own; a commit with a suffix is grouped by it, not by its merge; a `git pull` inside a pull request's branch stays in that pull request, any other merge, such as `git pull` on the mainline, `Merge tag`, a plain `Merge branch 'x'`, or a merge of the mainline into a branch, groups nothing), and then when their subjects name the same ticket key (`[A-Z][A-Z0-9]+-\d+`, not words like `UTF-8`, `SHA-256`, or `CVE-2024`) within 14 days of the first of them. A change's files are the union of its commits' files and its size, which the 50-file limit (`thresholds.maxCommitFiles`) judges, counts the files of their earlier lives too. The direct commits of an integration branch belong to no change: a pull request that names a release or `develop` branch (`main`, `master`, `develop`, `dev`, `staging`, `release/…`, `release-1.2`, `stable-2.x` and the like) as its source, or whose branch itself contains pull request merges or squash-merged pull requests (a `(#12)` suffix, `Merged PR 12: …`, `Pull request #12: …`), is a release and not one change, while the pull requests merged into that branch keep their own changes. A pull request of more than 30 commits is not one change, and a ticket does not join pull requests or commits into a change of more than 50 files or 30 commits: those commits stay apart. Mechanical commits never join one. `Report.logicalChanges.by` is `pr`, `ticket`, `mixed`, or `commit` (nothing was joined, every change is one commit), `count` the changes of the window before the size limit, `largest` the most commits one holds. `revisions` and line counts stay per commit, and each window of `--compare` is grouped on its own.

**Indentation complexity** — the sum of logical indentation levels over a file's non-blank lines. A language-agnostic proxy for structural complexity.

**Weighted lines** — a file's size as the score sees it: every non-blank line counts 1 plus its indentation level, so flat files (barrels) keep their weight and nesting adds to it.

**Hotspot** — a file that is both large or complex and frequently changed. Its **score** (0..1) is the product of its log-max-normalized revisions and weighted lines.

**Change coupling** — two files that repeatedly change in the same changes. Coupling across distant directories signals a missing or misplaced module boundary.

**Coupling degree** — `shared changes / mean(changes of both files)`, 0..1, where a change is a logical change and a file's `FileStats.changes` is the number of them that touched it, large ones included (a file edited in three commits of one pull request and in one other pull request has 2 changes and 4 revisions; a pair that shares both pull requests has degree 1). Shared and per-file counts use the same unit, so a pull request of many commits does not lower any degree. Symmetric; ranks coupled pairs.

**Co-change probability** — `shared changes / changes of one file of the pair`. Directional: how likely a change to that file also changes the other. `inspect` shows it for the focused file, `analyze` for both files of a pair.

**Test pair** — a coupled pair where one file is the other's test (`Coupling.testPair`). The test has a suffix (`.test`, `.spec`, `_test`, `_spec`) and either sits beside its source (`a.ts` and `a.test.ts`) or lies below a **mirrored test directory** (`test`, `tests`, `__tests__`, `spec`, `specs`, `e2e`) whose mirror holds the source: the same path with that directory removed or replaced by `src` or `lib` (`src/a/b.ts` and `test/a/b.test.ts`, `lib/x.ts` and `__tests__/x.test.ts`, `packages/p/src/y.ts` and `packages/p/test/y.test.ts`, `src/x.ts` and `src/__tests__/x.test.ts`). A file below a test directory without a suffix (a helper, a step file such as `login.steps.ts`, a mock) is test code but nobody's test, a test file below a `fixtures` or `__fixtures__` directory is never mirrored to a source, and the test support directories (`testing`, `test-utils`, `test-helpers`, `__mocks__`, `mocks`, `__snapshots__`) add no pairing of their own: their files are test code (see **Test code**), and one of them can still be a source or a suffixed test beside its partner (`src/testing/a.ts` with `src/testing/a.test.ts`). No fuzzy name matching pairs files elsewhere in the tree. Expected coupling, never a modularization smell.

**Co-change breadth** — the number of distinct other universe files (contract files included, ubiquitous ones not) a file changed together with in counted changes (at most `maxCommitFiles` files each), however rarely. A **hub** is a hub candidate (at least `hubMinRevisions` logical changes, `FileStats.changes`, not test code) whose breadth is at least `hubMinBreadth` and among the widest `hubTopShare` of the candidates, ties at the cut-off included; it is explained with a reason line, even when no single pair is coupled strongly enough to report.

**Module** — the unit the report groups universe files into. A **package** is a directory, other than the repository root, with a tracked manifest (tracked is enough: an ignore rule that matches it does not matter; `package.json`, `go.mod`, `Cargo.toml`, `pyproject.toml`, `pom.xml`, `build.gradle`, `build.gradle.kts`, or `*.csproj`); a file belongs to its nearest enclosing package. Files outside every package form **directory** modules, cut at the first depth where they split into at least two directories (at the first level when no depth does); root files form `.`. When that leaves fewer than two modules, all files are regrouped by directory. A module that holds more than 70 % of the universe files, and at least 20, is **dominant**: its files are split by the same directory rule, again while a part is dominant, until none is or no directory splits the last one (a module that big has nearly every commit inside it, so its cohesion says nothing; a smaller one is left alone). A package is split only when no other package with files in the analysis exists (a package of test code alone, such as a fixture's manifest, does not count): the largest of several packages is a boundary someone declared and stays one module, however large. A split package becomes directory modules but stays importable by its name, and its manifest still names entry points, which fall to the piece that holds them; usually that is the entry file alone, a module of its own, so the leakage and depth of the split code come out `null`. Beyond the 20-file floor for a dominant module there is no size floor: every package among others is a module.

**Cohesion** — of a module, `changes touching only this module / changes touching it`, over counted changes (a change that touched a contract file housed in the module touched the module; a contract file outside every module counts as another place); `null` without counted changes. Its **partners** are the other modules those changes touched, most shared changes first. A coupling that **crosses a module** joins files of different modules; that is stated neutrally, since an app legitimately changes with the library it uses. A module is **ranked** when it has at least `minModuleCommits` counted changes (`max(5, ceil(1% × couplingCommits))`) and is not **test-only**; the report, terminal, and viewer list ranked modules first, least cohesive first.

**Test code** — a file whose name has a test suffix (`.test`, `.spec`, `_test`, `_spec`) or that lies below a directory named `test`, `tests`, `__tests__`, `spec`, `specs`, `e2e`, `fixtures`, `__fixtures__`, `testing`, `test-utils`, `test-helpers`, `__mocks__`, `mocks`, or `__snapshots__`, except that a contract file is never test code, wherever it lies (`spec/main.tsp` is an interface definition, not a test). A **test-only module** (`Module.testOnly`) consists of test code alone. Never ranked: its cohesion says nothing about the design.

**Entry point** — in the module sense, a file that makes up a module's public interface (an entry point of a report is something else, see Entry point (of a report)). For a package: the files its `package.json` names in `exports`, `main`, `module`, or `types`, counting only JavaScript and TypeScript files and no `*.config.*` files (a `*` in a target matches any files, a target without extension finds the file with that name, and a `dist/` or `build/` target stands for the same-stem source under the module when one exists) and the conventional `index.{ts,tsx,mts,cts,js,jsx,mjs,cjs}`, `mod.rs`, `lib.rs`, `__init__.py` at the module root or its `src/`; for a directory module only the conventional files, plus, for a piece of a split package, the manifest-named files that lie in it. `--entry <glob>` replaces detection. Its **interface changes** are the counted changes that touched an entry point; its **implementation changes** those that touched any other file of the module that is not test code.

**Leakage** — of a module, `implementation changes that also touched an entry point / implementation changes`, 0..1; `null` without entry points or implementation changes. High leakage means changes inside the module keep changing its public API (a shallow or leaky module). A module is a **leaky interface** (`Module.leakyInterface`) when it is not test-only and its leakage is at least `minLeakage` over at least `minImplementationCommits` implementation changes; its entry points that changed in a commit that also changed the implementation get a reason. Unlike the cohesion ranking, that commit floor does not grow with the window: it only keeps a share of a handful of commits from counting. Low leakage behind an `export *` barrel does not prove a stable API, and an entry file that holds most of a module's code inflates leakage.

**Territory** — an area of the code in the report's non-overlapping tree (`Report.territories`), the unit for finding your way in a repository: a `package` (a directory with a manifest), a `folder`, or a `group` of sibling folders that keep changing in the same changes. It splits into its child folders when it is too big or when its folders change independently; folders that change together stay together. Test code belongs to the territory of the code it tests, and gets a `tests` territory beside the parts when that code is split; test code with no code beside it is a `tests` territory of its own, and files with no folder of their own, or folders waiting for a finer detail, sit in an `other` node, which is never a real territory. Unlike a module, a territory has a one-line `description` and a `splitReason`. See README, "How the numbers work".

**Detail** — how fine the territories are: level 1 is the first cut (top-level folders), up to level 6, each splitting the most valuable territories further. `Territories.details` lists the territories visible at each level; together they hold every file once.

**Recommended detail** — the finest detail with at most 25 territories (`Territories.recommended`; `other` nodes and test-only territories do not count) in which no bucket or node of loose files holds a folder that is hotter than the coolest territory opened beside it and holds at least 1% of all heat (`MIN_VISIBLE_HEAT`); when every detail with at most 25 territories hides such a folder, the finest of them, and its bucket is reported as it is: enough to tell areas apart, few enough to read. 0 for a universe without files.

**Split reason** — one line on a territory (`Territory.splitReason`) saying why it splits into its children: it is too big (with how many code files), its folders change independently (how much of its changes stay inside one), or it is a bucket of smaller folders opened one by one; it also says whether the parts still change together, and which folders stay together. Null for a territory that does not split.

**Territory fit** — how well one territory holds up to the way the code changes (`Territory.fit`, `TerritoryFit`), computed once per territory with the module measures' rules over the territories visible at the detail closest to the recommended one (`fit.detail`): `containment` (the share of the changes touching it that touch no other territory, `Module.cohesion` for territories), `radius`, the `partner` territory its changes most often reach into, the coupled file pairs that cross its boundary (`distantPairs`, `hiddenPairs`) and the cliques it belongs to, its `erosion`, its chronic and acute hotspots (`chronicShare` is the share of its code's heat in chronic ones), and its `fixDensity`. Test-only territories take no part: test code is no spread.

**Territory coupling** — `Report.territoryCoupling`: how often two territories at the recommended detail change in the same counted changes, the data of a territory matrix. Each entry is a pair of the `thresholds.maxCoupledTerritories` (24) hottest real territories (`a` sorts first by id, each pair once) with `sharedChanges` (counted by the code behind `fit.partner`), `distantPairs`, and `hiddenPairs` (the coupled file pairs between them, and those no import links). Only pairs that share at least `minSharedCommits` changes between territories ranked by `minModuleCommits` are listed. See README, "How the numbers work". v2 moves it under `coupling`.

**Territory clique** — `Report.territoryCliques`: a clique (see Clique) among the territories at the recommended detail, with `territories` (ids), `sharedChanges`, `weakestShare`, `heatShare`, and `codeHeatShare`; at most 50. An entry point of kind `clique` is read from the same list.

**Entry point (of a report)** — a place to start, one of the at most ten entries of `Report.entryPoints` that answer "where does the design fail, and where do we start?": a `kind`, a `rank`, the `territories` and `files` it concerns, its `evidence` (named numbers from the territory's fit, the clique, the copy family, or the unstable interface), a fixed-sentence `verdict`, and a `designMove`. It is not a module's entry point (see Entry point), which is a file of a module's public interface. The report has six kinds, each with its own rule:

The heat share of a file set is the share of all the production code's heat (the heat of a file is `changes × (loc + complexity)`; a test file holds none, in the total too: tests are change effort but not design) that its files hold, so every score is a share of the production code's heat at stake times how strong the weakness is, and scores of different kinds compare as the share of change effort at stake. A territory that is a bucket of smaller folders, loose files, or test-only code never qualifies. A territory that qualifies as both `boundary` and `hotspot` is one entry whose `kind`, `verdict`, `designMove`, and `score` are those of the stronger finding (a boundary on a tie) and whose `findings` list both, the stronger first. Each kind keeps its `maxEntriesPerKind` best entries. The best entry of each kind is always listed, whatever its score, as long as it passes the gates of its kind above (on a large repository the file-level kinds never reach half a percent of the change effort, and would vanish); the rest fill the list by score up to `maxEntries`, and every one of them scores at least `minEntryScore` (0.005: half a percent of the change effort). A file-level entry (`copies`, `hub`, `coupling`) whose files a higher ranked entry already names all of is left out. All the gates named above are in `thresholds`. `inspect` gives the territory of a file and the one it changes with most, with their `fit`, for the files that are in no entry.

**Design move** — what an entry point says to do, from one fixed template per kind with the paths filled in, not generated text: move a boundary (`boundary`), split a hotspot (`hotspot`), extract a shared abstraction (`clique`, `copies`), break up a hub (`hub`), centralize a contract (`coupling`).

**Verdict (of the HTML report)** — the one sentence on the report's first screen that answers whether the design holds up to the way the code changes. The viewer derives it from the report; no field carries it yet. It judges the territories at the recommended detail that are real parts of the design (packages, folders, and groups, not buckets of smaller folders or test code) and have at least `minModuleCommits` counted changes, since the share of a handful of changes is noise. A judged territory **leaks** when at most `maxEntryContainment` of its changes stay inside (the boundary gate of the entry points). The verdict takes the share of _all_ the repository's heat (the denominator of the fit map's tiles) that sits in leaking territories: below 20 % the design _holds up_, from 20 % _holds in parts_, from 50 % is _under strain_; an eroding trend (`erosion.verdict`) lowers it one level. When the judged territories hold less than half of all the heat there is no verdict (_not enough evidence_). Behind it are four facts: how many of the judged territories leak, the share of the change effort in the territories of the top three entry points (each territory counted whole, not only the files the entry names, and once), the trend of `erosion.locality` (the share of changes that stay in one module; higher is better; it is called a trend only from `minVerdictWindows` quarters on and when the engine finds it significant, otherwise the page says there are too few quarters), and `propagationCost`. The module-based `changeRadius` is not part of the first screen: it measures modules, the verdict territories.

**Fit map** — the HTML report's picture of all territories at the recommended detail: one tile each, area the square root of its heat share with a floor of 0.07 (a territory with less heat than 0.5 % is drawn as large as one with exactly that, so small territories stay readable), color its containment on the cohesion ramp, one numbered marker for the best entry point that concerns it, with a count of the others, and an outline for the top three. A territory that is not judged (test code, no counted change, changes only in commits of more than `maxCommitFiles` files, or fewer than `minModuleCommits` counted changes) is hatched and its tile says why.

**Territory card** — the HTML report's card for one territory at the detail chosen in "Where the heat is" (the viewer derives it; no field carries it). Its face has a fixed shape: name, description, share of the change effort, containment (or why it is not judged), hottest file, the territory it changes with most (`fit.partner`), and at most three findings. A **finding** is a place to start that concerns the territory (its primary finding, then its others; the entry's finest territories and the territories of the files it names decide, so a place to start stays on its territory at a finer detail; one that concerns parts of the card's territory names every part, `in a, b`, and one about the territory the card is part of says `within x`), or, when no place to start about the territory itself says it, one of its own numbers in this order: eroding (`fit.erosion`), chronic hotspots (`fit.chronicFiles`), coupling across its edge (`fit.hiddenPairs`, else `fit.distantPairs`), many fixes (`fit.fixDensity` at least 15 points above the repository's share with at least `minModuleCommits` fixes). The rest wait in the expanded card, which also lists the territories whose files share coupled file pairs with it (from `couplings`; pairs with test code and between two contract files are left out, as in `fit.distantPairs`) and the territories inside it.

**Comparison window** — with `--compare <duration>`, the window of the same length that ends where the analysis window starts. Both are read in one pass over the history and measured over the same universe, with the same fixed limits (such as `maxCommitFiles`); `minModuleCommits` is derived per window, and the report's thresholds are the analysis window's. The report describes the analysis window, the comparison window only feeds the trends. The comparison window is **truncated** when it reaches back past the oldest commit of the repository or of a shallow clone, and **empty** (`previousRealCommits` 0) when no real, non-mechanical commit touched the universe in it: there is then nothing to compare.

**Trend** — how a file or module moved between the comparison window and the analysis window. A file's **score delta** is its score now minus its score then, each normalized within its own window, so it shows a shift in standing among the files rather than a change in raw revisions; a module's **cohesion delta** is the change in its cohesion, positive when it became more self-contained. A file with no revisions in the comparison window but some now is **newly active** (`trend.newlyActive`): its score delta is just its score, so it is never ranked as warming. A file deleted and recreated at the same path is judged by the file that exists today in both windows, never by its predecessor. A module's trend needs at least `minModuleCommits` counted changes in both windows. A trend is `null` without `--compare`, and where a window has no data to compare. The treemap draws it as _cooler_ (score fell) to _warmer_ (score rose).

**Import relation** — of a coupled pair, whether a static import links the two files: `Coupling.imports` is `a→b` when `a` imports `b`, `b→a`, `both`, or `none`; `null` when it is unknown. A file imports another when it names it in a static `import`, `export … from`, a dynamic `import()` with a plain string, a `require()`, the `import("…")` of a TypeScript type, or `new URL("./x", import.meta.url)`, or imports a module that hands it on (transitively): one that re-exports it with `export … from`, or has the import, or the `require()` call, inside an exported expression (the initializer of an exported variable, `export default <expression>`, `export { name }`, `export =`, `module.exports = …`, `exports.x = …`; a name stands for what its variable was initialized with and assigned, through any number of top-level names). Only a name that references the import counts (not a plain property key, a member after the dot, or a JSX attribute name), and not one used inside a function or class within that expression: `export const api = { go: () => run() }` does not hand on `run`, while a `require()`, `import()`, or `new URL(…, import.meta.url)` does wherever it is (an exported `() => import("./page")` hands on `./page`), and so do what a class extends and what its decorators name, which are evaluated with the class (an `implements` clause is a type reference and does not hand on). Functions are hoisted, and `Object.assign(module.exports, require("./t"))` and tsc's `__exportStar(require("./t"), exports)` put what they are given on the exports. A top-level name stands for the modules its own initializer loads or refers to, plus what is assigned to it or to a member of it at the top level (also inside `if` and `try`, never inside a function: `Form.Item = Item`, `impl = require("./t")`), so exporting `const helper = require("./h").helper` hands on `./h`. An exported `import X = …` and an exported type alias that names an imported type hand on too; an interface that extends one does not. Relative specifiers, workspace package names (the files their manifest maps `"."` to, among the files the package owns, or, for a package that owns none such as a folder above its sub-packages, among all files below it, unless a package that owns files claims the same name), and nothing else resolve to universe files. The relation is **unknown** (`null`) when a file is not TypeScript or JavaScript, does not parse, or lies behind an unavailable parser, and when no import links the pair but some module involved is not **accounted for**: the two files, every file they import, and every file those hand on through must be readable and, where they are parsed, load only universe files, Node built-ins (a bare name that a directory, or a code file without its code extension, of the repository also carries is not one), packages some manifest declares (or its `@types`), workspace packages, and tracked assets. A tsconfig `paths` alias, a `#` subpath import, a bundler plugin scheme, an undeclared package or one whose name two manifests claim, code outside the universe, a component file (`.vue`, `.svelte`, `.astro`), or modules loaded by an expression (`import(name)`, `import.meta.glob()`, `require.context()`) makes it unknown. In an `inspect` partner the same relation is seen from the inspected file (`file→partner`, `partner→file`).

**Hidden coupling** — a coupled pair whose import relation is `none`: the files change together without referring to each other, so the shared contract (duplicated logic, a protocol, configuration read twice) is invisible in the code. A file whose strongest non-test partner is hidden with a co-change probability of at least `minHiddenProbability` (0.5) gets a reason line. Test pairs are never called hidden.

**Copy family** — a connected group of files with largely the same content that keep changing in the same changes (`Report.copyFamilies`, `InspectResult` `copyFamily`): the same change applied to each copy. Among the coupled pairs that are no test pair, two files are **similar** when the **Jaccard index** of their sets of **shingles** is at least `minCopySimilarity` (0.5); a shingle is a run of five consecutive words of the file as the tokenizer reads it: identifiers and keywords as they are, every string literal and number as one placeholder, no whitespace, punctuation, or comments (`//`, `/* */`, `<!-- -->`, `#` at the start of a line); a file with fewer than 20 distinct shingles is too small to compare. A family reports its sorted `files`, the `similarity` range (`min`, `max`) over all pairs of its members (the weakest can lie below the threshold: A like B and B like C make a family although A and C share little), `sharedChanges` (counted changes that touched at least two members), and `changesToAll` (counted changes that touched every member: the fixes applied to all copies). A family is `testOnly` when every member is test code (see **Test code**); those rank after the others and stay out of the terminal's list. It says the files change in lockstep, never that anything is wrong: one adapter per entity or one config per environment is duplication on purpose.

**Distant coupling** — a coupled pair that lies far apart in the design (`Report.distantCouplings`, `Partner.distant`): its files are in different modules, or in directories at least `minLocalDistance` (3) hops apart within one. A pair with a test-code file (see **Test code**) is never distant, and neither is a pair of two contract files. A distant coupling ranks by `score = strength × reach × hidden × evidence`: `strength` is the **coupling degree**, `reach` is `1 + log2(1 + hops)` between the two modules' directories for a pair across modules (so at least 2.58, growing slowly so that deeply nested paths do not dominate) and the file distance over the largest distance among the distant pairs within one module (at most 1), `hidden` is 1.5 for **hidden coupling** and 1 otherwise, an unknown import relation included, and `evidence` is `min(1, sharedCommits / 10)`. A modularity violation in the sense of Mo, Cai, and Kazman: structurally distant files that change together. It says the change crosses a boundary, never that the boundary is wrong.

**Module coupling** — of two ranked modules (see **Cohesion**), the counted changes that touched both (`ModuleCoupling.sharedCommits`) and their `share` of the smaller module's counted changes: how much of the smaller module's history happened together with the other. A change that touched a contract file counts as a touch of the module it lives in. The data of a coupling matrix; `Report.moduleCoupling` lists the 200 pairs with the largest share that shared at least `minSharedCommits` changes.

**Clique** — a maximal group of at least three ranked modules of which every pair shares at least `minCliqueShare` (30 %) of the smaller module's counted changes and at least `minSharedCommits` changes, and of which at least `minSharedCommits` changes touched every member (`Report.cliques`, with `sharedCommits`, `weakestShare`, and a one-sentence `reason`). A group that fails the last rule is searched for the sub-groups that pass it; a clique inside another is dropped, and of two **variants** of one unit only the stronger stays (more changes touching every member, then more members, then path): two cliques are variants when their union is pairwise linked in the module pair graph and they have at least `min(n − 1, ceil(0.8 n))` members in common, `n` being the size of the larger; groups that share a core pair but whose other members never change together are different units. The sub-group search is bounded (the 1000 maximal groups with the best evidenced weakest link, then 500 intersections and 1000 distinct parts of a group); `Report.cliquesPartial` says a bound was hit. The group is one unit of change cut by module boundaries, or shares an abstraction that is missing.

**Change radius** — how many modules a counted change touched, over the modules of `Report.modules` (`Report.changeRadius`, `Module.radius`). A change counts for the module of each universe file it touched and, for a contract file, the module it lives in (a place that holds only contract files counts as a module), as for **Cohesion**, but test-only modules are left out (the test of a change is no spread), and a change that touched no other module is not measured. `changeRadius` reports the measured `changes` (which can be fewer than `window.couplingCommits`: changes that touched only files that are dead today, or no module, are not measured), the `median` (the lower median: the middle change, the earlier of two, so a whole number), `p90` (nine in ten changes touched at most that many modules, nearest rank), and `local`, the share of the changes that touched exactly one module. A module's `radius` is the median number of modules, itself included, touched by the measured changes that touched it. It answers whether the structure contains change: a design that holds keeps most changes in one module. It depends on the partition: finer modules give a larger radius, and a repository with one module has a radius of 1. Unlike cohesion, which asks how many of a module's changes stay inside, the radius says how many modules the others reached: a module's radius is 1 exactly when its cohesion (leaving test-only modules out of the count) is at least 50 %, so the radius adds information where cohesion is below that.

**Propagation cost** — how much of the code a change to one file drags along (`Report.propagationCost`; MacCormack, Rusnak, and Baldwin), read from co-change instead of dependencies. The graph's nodes are the files that are not test code and took part in at least `minSharedCommits` (3) counted changes (not the large ones that coupling leaves out), the fewest a file needs to be coupled at all (contract files included), and its edges are the reported couplings between two of them (`thresholds.minSharedCommits`, `thresholds.minDegree`). A file reaches another when a chain of at most `thresholds.propagationDepth` (3) couplings joins them; the cost is the mean over the nodes of the share of the other nodes they reach, 0 when no file is coupled and 1 when every file reaches all others, with the node count as `files`. A full closure would saturate near 1 on dense graphs, hence the depth limit. It is relative to the files that change regularly, so a repository whose code mostly stays still is not diluted by it, and it describes the window. The cost shrinks as the number of regularly changing files grows, so read it within one repository over time, not between repositories of different size.

**Unstable interface** — a TypeScript or JavaScript file that at least `minFanIn` (5) files import directly (its **fan-in**; test code is no dependent, and a file that only reaches it through a re-exporting barrel does not count), that has at least `minInterfaceChanges` (5) logical changes (`FileStats.changes`, so a pull request that took ten commits counts once), and more changes than the median of its dependents (`Report.unstableInterfaces`): every change to it risks all of them. It reports `changedDependents`, the dependents that changed in a counted change that also changed the file. Dependencies come from the parser for the files of coupled pairs and from a text scan (import and `export … from` statements, literal `require` and `import()` calls, comments ignored) for every other file, so an import that cannot be resolved to a universe file adds no dependent.

**Dependency direction** — the Stable Dependencies Principle, measured from change rates: an import edge between two modules that points from a module that rarely changes to one that changes often (`Report.dependencyDirection`). The imported module has at least `minModuleCommits` counted changes and at least `minVolatilityRatio` (2) times as many as the importing one, which may not have changed at all; test code and test-only modules take no part. The edges rank by `log2(ratio) × log2(1 + changesTogether)`: the imported module's changes over the importing one's (`ratio`), times the counted changes (`changesTogether`) in which a file of the importing module changed together with a file it imports. TypeScript and JavaScript only.

**Language adapter** — the engine's seam to a language: one small adapter per language, selected by file extension, that lists what a file imports and what it exports, and, cheaper and coarser, which specifiers it loads at all (read as text, for whole-repository questions such as fan-in). Only the TypeScript and JavaScript adapter exists; the CLI injects its parser (`oxc-parser`), so the engine depends on no parser.

**Depth** — of a module (`Module.depth`), how much implementation sits behind how much interface: `{ exports, implementationLines, linesPerExport }`. `exports` is the number of distinct names its entry points export (a name that several entry points export counts once), following `export * from` within the module (as in ECMAScript: the file's own export wins, `default` is not forwarded, and a name that two `export *` sources export as different bindings is exported by neither), `export { x } from`, and `export * as ns from`; `implementationLines` is the `loc` of its files that are neither entry points, test code, nor tool configuration (`*.config.*`); `linesPerExport` is their quotient. A **deep module** has few exports over much implementation (many lines per export), a **shallow module** a wide interface with little behind it (few lines per export). The terminal lists the shallowest ranked modules. Depth is `null` where it cannot be told exactly (see `Module.depth`), never zero; it describes the code as it is now, not the window.

**Series** — the last 24 months or more of history cut into consecutive windows of about a quarter of a year (91 days) each, oldest first, at most 12, equal in length, the last ending at `window.until` (`Report.series`, starting at `Report.seriesSince`). The series covers at least the last 24 months whatever `--since` or `--compare` say, or the whole history if that is shorter (it starts at the oldest commit), and a longer analysis window extends it, so it can start before `window.since`; the measures of the window itself (hotspots, couplings, modules, radius, …) keep using `window`. A span shorter than about 4.5 months (20 weeks, one and a half quarters) is not cut at all, and the windows grow longer than a quarter once the span covers more than three years (36 months, 12 windows). They come from the one read of the history, which starts at the series start: a window groups, couples, and counts only the commits that landed in it, so a pull request across two windows is split between them, and the slices are classified over the series span (reverts, re-lands, and duplicates are paired inside it, and the merges that group commits into pull requests are read from its start), while the numbers of the analysis window itself are classified over the window span, as if it were read alone, so they equal those of a run that reads only the window; a commit can therefore be mechanical in a slice and not in the window, or the other way. Each reports its `changeRadius` and `propagationCost` and whether it is **active**: at least `minWindowChanges` (10) counted changes. Nothing below counts an inactive window.

**Erosion** — whether the design keeps containing change over the series. A robust line (Theil–Sen: the median of the slopes between every two active windows, and the median intercept, so one odd window cannot turn it) is fitted through a measure over the active windows and read at the first and last of them (`TrendLine`: `from`, `to`, `slope` per window; the values are the line's own, not held to 0–100 %). The repository's `Report.erosion` fits the share of changes that stay in one module (`changeRadius.local`). The verdict is `eroding` only when the line fell, and `improving` only when it rose, by at least `minErosionShift` (10 points) **and** at least `minErosionSigmas` (2) standard errors of that shift, otherwise `holding`; `unknown` with fewer than `minTrendWindows` (3) active windows. The same verdict must also follow from the active windows without the first and the last (a line fitted through the others, and the same gate), which needs at least `minVerdictWindows` (5) active windows: with three or four the verdict is `holding`, so one odd window at either end cannot decide it. The standard error is that of a weighted least-squares line through the windows' shares, whose variance is binomial, `p(1-p)/changes` with `p` the pooled share (not below 5 % or above 95 %), widened by 15 % for the Theil–Sen estimator and for changes that burst together; a flat design reads `holding` in more than 95 % of simulated cases from 60 changes a year up, and one odd window does not decide. The verdict describes the **active period**: inactive windows are left out wherever they lie, so they can neither cause nor hide a verdict, and a quiet end of the series is reported separately as `Erosion.inactiveSince`, the start of the run of inactive windows that ends it (null when the last window is active). The propagation cost gets a line for context, not for the verdict. A module's `Module.erosion` fits its cohesion over the windows in which it had at least `max(minWindowChanges, minModuleCommitsFor(the window's counted changes))` counted changes, with the same gate (`verdict`), the cohesion of every window, and `recent` (evidence in one of the last two windows).

**Chronic hotspot, acute hotspot** — how old a hotspot is (`FileStats.heat`). A file is **hot** in a window when it has revisions there and its score, computed from the window's revisions, is among the best `hotTopShare` (a tenth, rounded up, ties included) of the non-test files with revisions in the window. The windows that count for a file are the active ones from the first window in which it has a revision (all git shows of when it appeared). It is **chronic** when at least `minTrendWindows` (3) of them lie before the last two windows and it was hot in at least half of those and in at least half of all that count for it (the last two included): a design problem rather than a feature being built, and not one that cooled long ago. The last two windows do not count towards chronic, so a series needs at least five windows (about 15 months of history; the default 24 months give eight) before any file can be chronic. It is **acute** when it was hot in both of the last two windows and in fewer than half of the windows that count for it before them, with an active window before them to compare with: current work; a file hot in every window of a series too short to call it chronic is neither. A file that is neither has no `heat`, and neither has test code.

**Fix density** — the share of counted changes whose commit subjects say they fix something (`Report.fixDensity`, `Module.fixDensity`). A subject is a fix when it has the `fix`, `hotfix`, `bugfix`, or `revert` type of Conventional Commits (`fix(scope)!: …`), starts with `Revert "`, or has `fix`, `fixes`, `fixed`, `fixing`, `bug`, `bugfix`, or `hotfix` as its first word, unless `bug` is followed by a ticket number (`Bug 1234 - …`, `BUG-12`, `bug #7`), which names a ticket, or has a lowercase scope, a colon, and `fix`, `fixes`, or `fixed` after it (`compiler: fix crash`, but not under a Conventional Commits type such as `feat:`); a change of several commits is a fix when more than half of them are. A module also counts the fixes that **span** modules: those that also touched another module that is not test-only, which mark the boundary as fragile. It is **known** when at least `minConventionShare` (5 %) of the changes have a fix subject (by any of the rules above, so a team that writes free text and often starts with "Fix" gets a share) or another Conventional Commits type (`feat`, `docs`, `chore`, …); below it the subjects say too little, and the fix density is unknown, never 0.
