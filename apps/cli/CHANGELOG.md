# codeheat

## 0.3.0

### Minor Changes

- 91a2594: Report how far a change spreads. `analyze --json` gains two fields:

  - `changeRadius`: how many modules the counted changes (logical changes, like cohesion) touched, as the `median` (the modules a typical change touches), `p90` (nine in ten changes touch at most that many), `local` (the share that stays in one module), and the number of measured `changes`. Test-only modules are left out of every change, since the test of a change is no spread, and a change that touched no other module is not measured. It depends on the detected modules: finer modules give a larger radius.
  - `propagationCost`: the mean share of the other files a file reaches through chains of at most three couplings (the reported `couplings`, so at least 3 shared changes and a degree of 0.3), over the files that are not test code and took part in at least 3 counted changes (large changes are not counted), together with the number of `files` it ran over. 0 means no file is coupled, 1 that everything reaches everything; the depth limit keeps dense graphs from saturating. `thresholds.propagationDepth` reports the limit. The cost shrinks as the number of regularly changing files grows, so it is meant to be compared within one repository over time, not between repositories; the terminal does not show it.

  Each module gains `radius`, the median number of modules touched by the counted changes that touch it (1 means its changes usually stay inside), which `inspect` shows with the file's module. The terminal prints one sentence under the summary line, for example "Across 170 changes, a typical change touches 1 module; 9 in 10 touch at most 3 modules; 64% stay in one module." Both new report fields are `null` where there is no data.

- 03269b6: Include contract files in coupling: interface definitions and schemas (`.tsp`, `.proto`, `.graphql`, `.gql`, `.avsc`, `.thrift`, `.smithy`, `*.schema.json`, and `openapi.*`, `asyncapi.*`, `swagger.*` in YAML or JSON) now show which code follows them. They get no score, rank, or complexity and never appear in `files`, module sizes, leakage, or depth, but they couple with code, count as a touch of the module they live in for cohesion, and are marked `(contract)` in the terminal. A contract outside every module (a code-free `spec/` folder beside the packages) lives in that folder, and a module that changes with it lists it in `partners` with `contractsOnly: true` (`spec (contracts)` in the terminal), so a design-first package that loses cohesion to its contracts shows why.

  `analyze --json` gains `contracts`, `totals.contracts`, `ubiquitousFiles`, `Coupling.kinds`, `Module.partners[].contractsOnly`, and the thresholds `ubiquitousShare` and `ubiquitousMinCommits`; `inspect` partners gain `kind` and the result gains `contractFiles`. `couplings` now lists pairs with a code side first and pairs of two contract files after them, so `--limit` keeps code pairs, and the terminal's coupling table leaves contract pairs out like test pairs. Commits that touch only contract files now count in `window.commits` and `window.couplingCommits`, which can move `minModuleCommits` and the denominators of module cohesion slightly. A contract file that changes in more than 30 % of the counted commits (a central schema every change touches) is listed in `ubiquitousFiles` and left out of every pair. `inspect api/orders.tsp` now says that it is a contract file and to inspect the code that changes with it (exit code 4 when nothing else matched). `.proto`, `.graphql`, and `.gql` are no longer scored as code, and `tsp-output/` joins the excluded output directories. `--exclude` removes contract files, `--include` replaces the contract list like the language list, and there is no new flag.

- 83ff535: Find copy families: files with largely the same content that keep changing in the same commits, the same fix applied to each copy. Among the coupled pairs (a file and its own test excluded), files whose content overlaps by at least half (Jaccard index over runs of five words, comments and formatting ignored) form a family. `analyze --json` lists them in `copyFamilies` with `files`, the `similarity` range, `sharedChanges`, and `changesToAll` (commits that touched every member), `inspect --json` names the family of a file as `copyFamily`, `thresholds.minCopySimilarity` reports the limit, and `--limit` cuts `copyFamilies` like the other lists. Families of test code only are marked `testOnly`, rank last, and stay out of the terminal's list. The terminal shows the first five others under "Copies" and, in `inspect`, a line such as `changes with its 2 copies: …`. A family says the files change in lockstep, not that anything is wrong.
- 56ff4f4: Rank the places where structurally distant code keeps changing together, and add two scaling signals. Everything below counts logical changes, like the coupling it builds on (so `sharedCommits` and `commits` fields say changes, and a pull request that took ten commits counts once). `analyze --json` gains:

  - `distantCouplings`: coupled pairs in different modules, or far apart within one module, without test code and pairs of two contract files. The score is `strength × reach × hidden × evidence`: `reach` is `1 + log2(1 + hops)` between the module directories (so deeply nested paths do not dominate) or the share of the largest file distance within one module, `hidden` is 1.5 for a pair no import links, and `evidence` is `min(1, sharedCommits / 10)`, so a pair that met in three changes does not outrank one that met in eleven.
  - `moduleCoupling`: per pair of modules the shared counted changes and the share of the smaller module's changes, the data of a coupling matrix.
  - `cliques`: groups of at least three modules of which every pair shares 30% of the smaller module's changes and that at least three changes touched in full, each with a one-line reason. A group in which no three changes touched every member is searched for its sub-groups that did; a clique inside another is dropped, and two variants of one unit (their union pairwise linked, nearly all members in common) are reported once, as the stronger. `cliquesPartial` is true when the bounded sub-group search gave up on a very varied group.
  - `unstableInterfaces`: TypeScript and JavaScript files that many files import directly and that change more often than their dependents, with the dependents that changed with them.
  - `dependencyDirection`: imports from a module that rarely changes to one that changes often (the Stable Dependencies Principle, measured from change rates). Each edge carries `ratio` (the imported module's changes over the importing one's) and `changesTogether` (counted changes in which a file of the importing module changed together with a file it imports); the list ranks by `log2(ratio) × log2(1 + changesTogether)`, so a framework that everything imports does not fill it.

  `inspect` partners carry `distant`, `thresholds` report the new limits (`minLocalDistance`, `minCliqueShare`, `minFanIn`, `minInterfaceChanges`, `minVolatilityRatio`), and `--limit` cuts the new lists like the others. The terminal shows the five best distant couplings and a line per clique ahead of the plain coupling table, marks distant partners in `inspect`, and lists the first unstable interfaces and stable-to-volatile imports. Dependencies for the two scaling signals are read from every non-test code file, by the parser for the files of coupled pairs and by a text scan for the rest, which adds a few percent to the time of an analysis.

- ba58594: Count the commits of one pull request or ticket as one change for coupling, module cohesion, interface churn, breadth, and copy families. Commits belong together when they share a squash-merge `(#123)` suffix or a merge commit that names a pull or merge request (GitHub, Bitbucket, GitLab, Azure DevOps) brought them in, or name the same ticket key within 14 days (other merges, such as `git pull`, tags, or merges of the mainline into a branch, group nothing); the direct commits of an integration branch (a merge that names a release or `develop` branch, or a branch that itself contains pull request merges or squash-merged pull requests) stay single commits; a pull request of more than 30 commits and a ticket group of more than 50 files or 30 commits are not joined, and mechanical commits never join. `window.couplingCommits`, `sharedCommits`, and the module commit counts now count these changes (fewer, larger units: couplings that only the commits of one pull request shared disappear, and cohesion falls where pull requests reach across modules), while `revisions` stay per commit. `FileStats.changes` (and `ContractFile.changes`) is the number of changes that touched a file, and coupling degree, co-change probability, and the hub floor compare shared changes with it. The report gains `logicalChanges: { by, count, largest }` (`by` is `pr`, `ticket`, `mixed`, or `commit` when no commits were joined).
- ca64445: Mechanical commits no longer count as revisions, changed lines, or coupling, cohesion, and interface-churn evidence: exact renames and mode changes, whitespace-only diffs, a revert together with the commit it reverts (when both are in the window), commits whose patch id equals that of an older commit on a parallel line (cherry-picks, backports), and commits listed in `.git-blame-ignore-revs`. They still count in `window.commits` and still carry a file's history across renames. The report gains `mechanicalCommits`, a count per kind, plus `window.realCommits` and `comparison.previousRealCommits`, the commits that are not mechanical. A revert pairs with its original only when it undoes it exactly over the analyzed files (same paths, mirrored line counts, and each file either restored to the object it had before the original or changed by a patch equal to the original's reversed; lockfiles and other files outside the universe do not count); a patch applied again on top of an older copy (a re-land) counts as a real change. A re-indent is never whitespace-only where indentation is syntax (Python, Starlark, F#, Haskell, Scala, YAML, Makefiles, and similar). With `--compare`, a window without real commits has nothing to compare: file trends are `null`, and the terminal and the viewer say the window has only mechanical commits. Scores, couplings, and module cohesion of repositories with such commits change accordingly.
- b66af3b: Count test support directories as test code: a file below a directory named `testing`, `test-utils`, `test-helpers`, `__mocks__`, `mocks`, or `__snapshots__` is now test code like one below `test` or `fixtures` (a contract file stays a contract). Such files are no longer hub candidates, are marked `FileStats.test`, count as test code in copy families (`testOnly`), leave `distantCouplings` and `unstableInterfaces`, and do not count as implementation lines in a module's `depth` or as implementation commits; a module made only of them is test-only, and a package of them no longer counts as another package when a repository's modules are split. A production package or folder that happens to carry one of these names is read as test code too; `--exclude` cannot override that yet.

### Patch Changes

- 8ba689c: Recognize tests mirrored under `test/`, `tests/`, `__tests__/`, `spec/`, `specs/`, or `e2e/` as test pairs of their source (`src/a/b.ts` with `test/a/b.test.ts`, `lib/x.ts` with `__tests__/x.test.ts`), so `Coupling.testPair` is true for them. Fix three bugs found on real repositories: test step files and mocks below a test directory were reported as hubs, a tracked manifest that a `.gitignore` pattern matches was not detected as a package, and a workspace package without files of its own (a folder above its sub-packages) could not be imported by name.

## 0.2.0

### Minor Changes

- 25ceef7: Report how many different files each file changes together with (`breadth` in the JSON report, shown by `inspect` and in the treemap panel), and explain hub files such as barrels that couple weakly to many files. Only files changed at least 5 times that are not tests can be hubs; `thresholds.hubMinRevisions` states the limit.
- e8ffa90: The coupling table of `analyze` now shows, for each pair, how likely a change to either file also changes the other (`a → b` and `b → a`), next to the symmetric degree. The JSON report is unchanged.
- 978e9fd: Flag hidden coupling: coupled TypeScript and JavaScript files with no import between them. Every coupling in the JSON report gains `imports` (`a→b`, `b→a`, `both`, `none`, or `null` when it cannot be told: a file is not TypeScript or JavaScript, does not parse, no parser was available, or an import could not be resolved), and every `inspect` partner gains `imports` seen from the inspected file (`file→partner`, `partner→file`, `both`, `none`, or `null`). `none` is hidden coupling. A file whose strongest non-test partner is hidden, with a co-change probability of at least `thresholds.minHiddenProbability` (0.5, new), gets a reason line ("changes with X in 70% of its commits without an import between them"). The terminal coupling and partner tables gain an import column, and the treemap badges and outlines such partners in their own color. Imports are resolved from relative specifiers (as TypeScript does, including `.js` for `.ts` and `index` files) and workspace package names, and follow what a module hands on: `export … from`, and imports or `require()` calls inside an exported expression (an exported initializer, `export default`, `module.exports = …`). `none` is only reported when every module involved is accounted for (universe files, Node built-ins, declared dependencies, workspace packages, assets); tsconfig `paths` aliases, `#` imports, bundler plugin schemes, and modules loaded by an expression (`import(name)`, `import.meta.glob()`) make the relation `null`.

  The imports are read with `oxc-parser`, now the package's one runtime dependency, loaded lazily. codeheat now requires Node.js 22.12 or newer (it was 22). If the parser's native binary cannot load, codeheat says so once on stderr, reports `imports: null`, and everything else works as before. `analyze` needs more time and memory on a large repository.

- c083072: Report interface churn against implementation churn per module. Entry points come from `package.json` (`exports`, `main`, `module`, `types`) and conventional files (`index.ts`, `mod.rs`, `lib.rs`, `__init__.py`, …), or from the new repeatable `--entry <glob>` flag of `analyze` and `inspect`. Each module in the JSON report gains `entryPoints`, `interfaceCommits`, `implementationCommits`, `leakage` (the share of implementation commits that also touched an entry point), and `leakyInterface`, and `thresholds` gains `minLeakage` and `minImplementationCommits`. Entry points that changed with the implementation of a module with a leakage of at least 50% over five implementation commits get a reason line. `analyze` lists the leaky interfaces in the terminal, `--entry` warns on stderr when it matches no file, and the treemap panel shows a module's entry points and leakage.
- 3bfa9fc: Group files into modules (workspace packages, otherwise directories) and report how often each module's changes stay inside it. The JSON report gains `modules`, `FileStats.module`, `Coupling.crossesModule`, `totals.modules`, and `thresholds.minModuleCommits` (1% of the counted commits, at least 5); each module says whether it is `testOnly`, and `modules` lists the ranked ones first. `inspect` adds the modules of the matched files and marks partners in another module with `crossesModule`; `analyze` lists the least cohesive modules in the terminal, and the treemap can color tiles by module cohesion.
- a2151f8: Measure module depth: how many lines of implementation sit behind each exported symbol. Each module in the JSON report gains `depth`, `{ exports, implementationLines, linesPerExport }`, for TypeScript and JavaScript modules: `exports` counts the distinct names of the module's entry points, following `export * from` within the module (a name that several entry points export counts once), and `implementationLines` the lines of its files that are neither entry points, test code, nor tool configuration. It is `null` whenever the exports cannot be told exactly (no entry points, another language, a file that does not parse, CommonJS or `export =`, an `export *` from a package, another module, or one that resolves to several files, two bindings of a name that cannot be told apart, no exports, no implementation files) and without the parser. `analyze` lists the five shallowest ranked modules in the terminal, `inspect` states the depth of each matched file's module, and the treemap panel shows it in the interface section.
- b4a3e9c: Split a module that holds most of the code. A module with more than 70% of the files used to stay whole whenever another module existed, so a repository with one package and a small `scripts/` directory (or `src/` beside a small `test/`) had one module that said nothing. It is now cut by directory with the rule that already applied to a repository of a single module, and again while a part still holds more than 70%, provided the module has at least 20 files. A package is split only when no other package with files in the analysis exists (a package of test code alone does not count): the largest of several packages stays one module, however large. The pieces of a split package are directory modules; the package stays importable by its name, and the files its `package.json` names are entry points of the piece that holds them. After a split the entry file usually forms a module of its own, so the leakage and depth of the split code are `null`. Analyzing a lone package directly (`analyze packages/app`) now resolves it by its name too. The JSON report keeps its shape; `modules`, `FileStats.module`, `crossesModule`, and the cohesion, leakage, and depth figures follow the new boundaries for repositories where the rule applies.
- 86e551f: `codeheat analyze --compare <duration>` compares the latest window of that length with the one before it and reports how hotspots and module cohesion moved. Combining it with `--since` is a usage error (exit 2).

  The JSON report gains `comparison` (the previous window with `previousCommits` and `previousTruncated`), `FileStats.trend` (`previousScore`, `previousRevisions`, `scoreDelta`, `newlyActive`), `FileStats.test`, and `Module.trend` (`previousCohesion`, `cohesionDelta`, only for modules with enough commits in both windows). The trends and `comparison` are `null` without `--compare`. Scores are normalized within each window, so a delta shows a shift in standing among the files. The terminal view adds a "Biggest changes" section with the five source files that got hotter most, the three highest-ranked newly active source files, and the five modules whose cohesion moved most. Test files are left out, and a file with no revisions in the previous window is newly active, not warming. The treemap gains a third color mode, Change (`#mode=change`), from cooler to warmer; newly active files and files without data are hatched. An empty or cut-off previous window is reported as such, in the terminal and, for a shallow clone, on stderr.

### Patch Changes

- 59c244a: Explain an empty report in the HTML treemap: instead of a blank area, the stage says the analysis universe has no files and points to the path argument, `--include`, and `--exclude`, and the side panel drops the empty hotspot list.
- b90c87b: Report a fatal git error other than "not a git repository" (for example a dubious-ownership failure or a broken `.git/config`) with git's own message and exit code 1, instead of the misleading "not a git repository" and exit code 3. A bare repository or a `.git` directory, which has no work tree, still counts as not a git repository (exit code 3).
- a946d15: `codeheat analyze --html report.html` now exits 2 and suggests `--out report.html` instead of taking the file name as the path to analyze. It applies to any path ending in `.html` (case-insensitive) when `--html` is given without `--out`; write `./x.html/` to analyze a directory of that name.
- 181e537: codeheat analyzes the given repository even when run from a git hook.
- a77103c: `inspect` resolves a path without glob characters against the working directory, so `codeheat inspect b.ts` works from a subdirectory. Absolute paths work too; globs stay repository-relative.
- 91b1a77: The README's `inspect` example now uses an illustrative sample repository.
- 2629f00: A file that was deleted and later recreated at the same path no longer inherits the old file's history: its revisions, changed lines, coupling partners, module cohesion, and, with `--compare`, its trend come from the file that exists today. A deleted file that comes back with the very content it had, as with a revert, continues.
- 1bcb953: Print Windows paths such as `C:\Users\me\codeheat-report.html` as they are, so they can be pasted into a shell or file manager. Backslashes are now doubled only where they could be mistaken for a `\uXXXX` escape.

## 0.1.0

### Minor Changes

- d3c76bd: Add the `analyze` and `inspect` commands. `codeheat analyze [path]` prints the top hotspots and change couplings of a git repository, or the full ranked report with `--json`; `--since`, `--include`, `--exclude` and `--limit` shape the analysis and its output. `analyze` accepts a directory or a single file, warns on stderr about shallow clones, and never follows symlinks. `codeheat inspect <file-or-glob...>` shows the rank, metrics and co-change partners of files before you edit them. Exit codes: 0 success, 1 unexpected error, 2 usage error, 3 not a git repository or git missing, 4 `inspect` matched nothing.
- 9d07ead: Add `codeheat analyze --html`: a self-contained treemap (area = lines of code, color = hotspot rank) that opens in the browser. Click a file to see why it is hot and which files change with it; filter by path or glob. `--out <file>` chooses where it is written, `--no-open` skips the browser.
