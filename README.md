# codeheat

See where a codebase hurts. codeheat reads your git history and shows two things:

- **Hotspots** — files that are big or deeply nested _and_ change all the time. That is where bugs, merge conflicts, and slow reviews concentrate.
- **Change coupling** — files that keep changing in the same changes. When they sit in different modules, a boundary is in the wrong place, and anyone (human or agent) who edits one file without the other ships a half-done change. Interface definitions and schemas (TypeSpec, Protocol Buffers, GraphQL, OpenAPI, …) take part as contract files: when the contract is the pacemaker, the code that follows it shows up as its partner.
- **Hidden coupling** — coupled files with no import between them (TypeScript and JavaScript). Nothing in the code points at the dependency, so duplicated logic, a wire protocol, or configuration read in two places goes unnoticed until one side changes alone.

Humans get a treemap and a ranked list of where to start. Agents get ranked, explained JSON.

```bash
npx codeheat analyze             # top hotspots and couplings in the terminal
npx codeheat analyze --html      # interactive report in the browser: verdict, where to start, treemap
npx codeheat analyze --json      # ranked, bounded report for agents and scripts
npx codeheat inspect src/billing/invoice.ts   # what to know before editing a file
```

Requires Node.js 22.12 or newer and `git` on your PATH. Works for any language; hidden coupling and module depth (below) are reported for TypeScript and JavaScript.

## The HTML report

`codeheat analyze --html` writes `codeheat-report.html` — one self-contained file, no network access — and opens it. It follows light and dark mode and reads on a phone. It opens on the answer to one question, _does your design hold up to the way your code actually changes?_, and shows three things at once, without scrolling at 1440 × 900:

- **The verdict**, one sentence for the whole repository: how much of the change effort happens in territories whose changes keep reaching into their neighbors, and whether that is getting better or worse. A line under the question says what a territory and its boundary are. Behind the verdict are the numbers it rests on: how many of the territories with enough changes leak (at most 75 % of their changes stay inside), how much of the effort sits in the top three places to start, the trend of the share of changes that stay in one module (called a trend only from enough quarters on), and the propagation cost. With less than half of the change effort in territories that can be judged, the page says there is not enough evidence instead of a verdict.
- **The fit map**: every territory at the recommended detail as one picture, with its name and what it is. Area is the share of the change effort (how often a file changed, weighted by its size and complexity; square-root scaled, so small territories stay readable), color is the share of its changes that stay inside it (dark violet in light mode, bright in dark mode: few), and hatching means the territory is not judged, and the tile says why: test code, no counted changes, changes only in commits of more than `maxCommitFiles` files (not counted for spread), or too few counted changes (below `minModuleCommits`) for its share to mean anything. A territory that is a place to start carries one numbered marker, its best rank in Where to start (`+2` when two more concern it); the top three are outlined. A territory the map is too small to label is in the list under it.
- **The top three places to start** as one-liners that link down.

Below that, **Where to start** is the ranked list of entry points: for each its rank, kind, territory or files, what is wrong, where a boundary leaks to, the design move, and the numbers behind it, with links to its territory on the fit map and to its files in the treemap. A report from an older codeheat without territories or entry points says so and still shows the treemap.

**Where the heat is** shows the territories as cards, hottest first, at the detail you choose with a slider over the report's levels (the recommended detail is marked and selected first; a level shows only that cut, and the fit map above stays at the recommended one). A card says how much of the change effort the territory holds, how many of its changes stay inside it (or why it is not judged, as on the fit map), its hottest file (test code only when there is no other code), the territory it changes with most, and the first three of its findings: the places to start that concern it (one that concerns a part of the card's territory names every part, one about a territory the card is part of says `within` it; a finer detail than the recommended one keeps them, since they are matched by the finest territories the entry names), then what its own numbers add that no place to start about the territory already says, in this order: eroding, chronic hotspots, coupling across its edge (hidden when no import links the pairs), many fixes (well above the repository's share). Test code and buckets of leftovers come last, drawn quieter. **Expand** adds the territory against the repository (share of the effort against share of the files, its changes against the changes that count in the window (`window.couplingCommits`), what stays inside against the median of the territories measured at that detail (`fit.detail`), fixes, hot files, how many territories a change touches, pairs across its edge, its widest file), all its findings with the verdicts, its hottest files, the territories whose files share coupled pairs with it (pairs with test code and between two contract files are left out, as in `distantPairs`), and the territories inside it with why it splits. A card links to its tile on the fit map and its files into the treemap. Detail 1 to 6 are only the report's levels; the report has no field for the cards, they are derived from `territories`, `files`, `couplings` and `entryPoints`.

**What changes together** comes next. The _territory matrix_ shows how often every pair of the hottest territories at the recommended detail (up to `maxCoupledTerritories`, 24) changed in the same changes (`territoryCoupling` in the JSON report): a cell is that number, the diagonal is the share of a territory's own changes that stay inside it (the color of the fit map), and the two halves mirror each other, so a pair reads the same from either side. A corner notch marks a pair with coupled files across its boundary and a dashed inner line a pair where some of them have no import between them (hidden coupling), so neither depends on color. Rows are named in full and numbered like the columns; the cell under the pointer or the keyboard focus (one tab stop, then the arrow keys, Home, and End) is read out in a sentence under the legend, such as "A and B changed together 12 times; no import between them (3 coupled file pairs)", and a pair that is not shown says so (fewer than `minSharedCommits` shared changes). A territory with fewer than `minModuleCommits` changes has no row; one note under the matrix names those ("Not compared, too few changes"). Under the matrix, three lists each show the evidence in numbers: the territories that change as one unit (`territoryCliques`, each linking to its tile on the fit map), the file pairs that change together across boundaries or far apart (`distantCouplings`, hidden coupling first), and the copy families that change in lockstep (`copyFamilies`, test-only families left out and counted), with the files linking to the treemap.

### The treemap

The **Map** section is the treemap of every file.

- **Area** is lines of code, **color** is hotspot rank: the darkest tiles are the hottest 2 % of the repository. Tiles are grouped by the territory that holds them, like a stock-market heatmap grouped by sector, with the folders of each territory inside it.
- **Group by** switches between _Territories_ (the default, the parts of the fit map) and _Folders_ (every file by directory). _Detail_ picks the level of the territories, from the coarsest to the finest, with the recommended one marked and the number of territories at each. **Show in the map** on a place to start, a territory card, or a tile of the fit map, groups by territory and fills the map with that territory alone; a bar above the map names it and says how many files it holds, and **Show all territories** zooms back out. Selecting a file elsewhere (from a card or the list of hotspots) zooms out to show it. A report from an older codeheat without territories groups by folder and shows no grouping controls.
- **Color by** switches between _Heat_ (hotspot rank), _Cohesion_ (the module's cohesion), and _Change_ (`#mode=change`): how a file's score moved against the window before, from cooler (blue) to warmer (orange). _Change_ needs a report made with `--compare`.
- **Click a file** to see why it is hot and which files change with it. Its partners light up wherever they live in the tree; partners in distant folders are the modularization smell to look for. A partner with no import to or from the file is outlined in magenta and badged _no import_: hidden coupling.
- **Filter** by substring (`billing`) or glob (`packages/*/src/index.ts`).

`--out <file>` picks the path, `--no-open` skips the browser. `--html` takes no value: `codeheat analyze --html report.html` exits 2 and suggests `--out report.html` (to analyze a directory named `x.html`, write `./x.html/`).

## Commands

### `codeheat analyze [path]`

| Flag                                  | Default          | Meaning                                                                                                                                                                                                                     |
| ------------------------------------- | ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `[path]`                              | whole repository | A directory (or file) inside a repository; only files under it are analyzed. Also works for a repository elsewhere: `codeheat analyze ../other-repo`.                                                                       |
| `--since <when>`                      | `12m`            | History window: `<n>d`, `<n>w`, `<n>m`, `<n>y`, or `YYYY-MM-DD`. Old churn says little about today.                                                                                                                         |
| `--compare <duration>`                | off              | `<n>d`, `<n>w`, `<n>m`, or `<n>y`. Reports the latest window of that length and how each file's score and each module's cohesion moved against the window before it. Replaces `--since`; giving both is a usage error.      |
| `--include <glob>`                    | language list    | Replaces the built-in list of ~50 source-code extensions and the contract list. A file that names a contract (see Contract files) stays one. Repeatable.                                                                    |
| `--exclude <glob>`                    | —                | Removes matching files, contract files too. Repeatable.                                                                                                                                                                     |
| `--limit <n>`                         | `25`             | Files, contract files, couplings, modules, copy families, distant couplings, module couplings, cliques, unstable interfaces, and dependency directions in `--json`, each; `0` for all. `totals` always tells the full size. |
| `--entry <glob>`                      | detected         | Files that form a module's public interface, instead of detecting them (see interface leakage below). Repeatable.                                                                                                           |
| `--json`                              | off              | One JSON document on stdout; everything else goes to stderr.                                                                                                                                                                |
| `--html`, `--out <file>`, `--no-open` | off              | The HTML report, see above.                                                                                                                                                                                                 |

### `codeheat inspect <file-or-glob...>`

Paths or globs. A path without glob characters is absolute or relative to the working directory, so `codeheat inspect b.ts` works inside `src/`, and a path that does not start with `./` or `../` is read as repository-relative when nothing exists at that place in the working directory; a glob is repository-relative (quote globs so the shell leaves them alone). A path outside the repository matches nothing. The whole repository is analyzed, so ranks and partners stay relative to all files. Takes `--json`, `--since`, and `--entry`.

### Exit codes

| Code | Meaning                                                                                   |
| ---- | ----------------------------------------------------------------------------------------- |
| 0    | Success                                                                                   |
| 1    | Unexpected failure (including a git command that failed, or an unwritable `--out`)        |
| 2    | Usage error, such as an unknown flag, an invalid `--since`, or `--compare` with `--since` |
| 3    | Not inside a git repository, or `git` is not installed                                    |
| 4    | `inspect` matched no file                                                                 |

## How the numbers work

- **Universe** — the files that count: tracked by git, not ignored (also files committed before a `.gitignore` rule existed), not marked `linguist-generated` or `linguist-vendored` in `.gitattributes`, not in `vendor/`, `node_modules/`, `dist/`, `build/`, `generated/`, `__generated__/`, `tsp-output/`, not minified or binary or larger than 1 MiB, and matching the language list, the contract list (below), or `--include`. Code files get a score; contract files only couple.
- **Contract files** — interface definitions and schemas whose changes drive changes in code: `.tsp`, `.proto`, `.graphql`, `.gql`, `.avsc`, `.thrift`, `.smithy`, JSON Schema files (`*.schema.json`), and OpenAPI, AsyncAPI, and Swagger descriptions by name (`openapi.*`, `asyncapi.*`, `swagger.*` in YAML or JSON). They are in the universe by default, and `--exclude` removes them. They take part in coupling (`Coupling.kinds` says which side is a contract, `inspect` partners carry `kind`, the terminal marks `(contract)`) and count as a touch of the module they live in (the nearest module above them; the root module only houses contracts at the top of the repository; any other contract outside every module, such as a `spec/` folder beside the packages that implement it, lives in the highest directory above it that holds no code, which is no module, and `partners[].contractsOnly` marks it, shown as `spec (contracts)` in the terminal) for cohesion and partners, but get no score, rank, or complexity, never appear in `files`, and count for no module's size, leakage, or depth. They are listed in `contracts` with their revisions and lines. A commit that touched only contract files counts in `window.commits` and `window.couplingCommits`. `couplings` lists pairs with at least one code side first and pairs of two contract files after them (the files of one API definition change together far more often than code does, so `--limit` keeps the code pairs); the terminal's coupling table leaves contract pairs out like test pairs. The output generated from a contract (`tsp-output/`, `generated/`, `__generated__/`) stays out: the contract and the code generated from it are linked through coupling. Their import relation is `null`. A contract file that changed in more than 30 % of the counted changes, and at least 10 of them (`thresholds.ubiquitousShare`, `ubiquitousMinCommits`), is **ubiquitous**: a central schema every change touches would couple to everything. It is listed in `ubiquitousFiles` and left out of every pair, breadth, and cohesion. `.proto`, `.graphql`, and `.gql` moved here from the language list: their indentation says nothing about an interface definition.
- **Revisions** — non-merge commits in the window that touched the file, following renames; mechanical commits (next item) do not count. A path that was deleted and later created again with other content starts afresh: only the file that exists today counts, not the one deleted at its path; a deleted file that comes back with the very content it had (a revert, or a re-land after a revert) continues. What a commit changed in the deleted file adds nothing to revisions, changed lines, coupling, breadth, module cohesion, interface churn, or trends, though the commit still counts in `window.commits`, and it still counts toward the 50-file cap, so a mass commit stays ignored for coupling even where most of its files have been deleted and recreated since. Deletions and creations made only inside merge commits are not seen (see Known limits).
- **Mechanical commits** — a commit that, as far as git can tell, changes the repository without changing what its code does says nothing about where the design is under pressure, so it adds no revisions, changed lines, breadth, cohesion, interface churn, or coupling evidence. It still counts in `window.commits`, and its renames still carry a file's history. `mechanicalCommits` in the report counts them per kind, and each commit has one kind, the first that applies: `ignored` (listed in `.git-blame-ignore-revs` at `HEAD`), `renames` (every change is a rename that kept the content, similarity 100, or a mode change; a rename that also edits the file is a real change), `whitespace` (the diff is empty under `git diff -w`, in a commit that touches no file of a language where indentation is syntax: Python and Starlark/Bazel files, F#, Haskell, Elm, Scala, Nim, YAML, Makefiles and similar, where a re-indent can change what the code does), `reverts` (a commit whose message says `This reverts commit <sha>` and the commit it reverts, counted together, when both are in the window and the revert undoes the original exactly: over the analyzed files (code and contract files of the universe; lockfiles, generated output, and other files outside it neither break nor make a pair) it touches the same paths and its line counts mirror the original's (it adds as many lines as the original deleted and the other way round), and every such file is confirmed undone, either because the revert restored it exactly (the file's object after the revert is the one it had before the original) or because the revert's patch for it equals the original's patch reversed (the lines changed are compared, not their context or position); a change of a file's type never confirms, and neither does a file whose changed lines are not valid UTF-8; a squash commit that names a reverted commit but does other work, a revert of only part of a commit, and a revert that keeps, rewrites, or replaces some of the change (even with the same line counts) all count normally; a revert whose original is outside the window changes the code inside it and counts normally; a revert that was itself reverted pairs with its reverter, which leaves the first commit as the one real change), and `duplicates` (a commit with the same `git patch-id --stable` as an older commit in the window that it does not sit on top of, such as a cherry-pick or a backport on a parallel line; the oldest counts; the same patch applied again on top of the commit that had it, a re-land after a back-out, changes the code once more and counts as a real change). Reverts and duplicates are paired inside one window, so with `--compare` each half is judged by what it holds. Whitespace and duplicates are only looked for in commits that could be one (equal line counts per file; the same paths and line counts as another commit), which keeps the extra `git` work small.
- **Logical changes** — commits that belong together count once for coupling, module cohesion, interface churn, breadth, and copy families (`revisions`, `linesAdded`, and `linesDeleted` stay per commit): the report's `sharedCommits`, `commits`, `localCommits`, `interfaceCommits`, `implementationCommits`, `changesToAll`, and `window.couplingCommits` count these changes, and where this page says "counted change" it means a counted change. Commits belong to one change when they share a pull request, which is a squash-merge subject that ends with the same `(#123)` (within 14 days of the first of them), or a merge commit that names a pull or merge request brought them in (GitHub `Merge pull request #12 from …`, Bitbucket `Merged in … (pull request #12)` or, for Bitbucket Server and Data Center, `Pull request #12: …` and `Merge pull request #12 in PROJ/repo from …`, GitLab `See merge request …!12`, Azure DevOps `Merged PR 12: …`; read with one extra `git log` over the window's merge commits (messages only), and, when one of them names a pull request, a second over the window's commits (parents and subjects) plus `git rev-parse HEAD` to start the walk at `HEAD`; a branch merged into another branch belongs to that inner merge, a commit with a `(#123)` suffix is grouped by it and not by its merge, and each branch of an octopus merge is its own change). A `git pull` merge inside a pull request's branch brings its commits into that pull request. Any other merge, such as the `git pull` merge `Merge branch 'main' of …`, `Merge remote-tracking branch`, `Merge tag`, a plain `Merge branch 'x'`, or a merge of the mainline into a branch, groups nothing, but the pull requests merged inside its branches still do, and then when their subjects name the same ticket key (`[A-Z][A-Z0-9]+-\d+` such as `PROJ-42`; words like `UTF-8`, `SHA-256`, and `CVE-2024` are no tickets) within 14 days of the first of them. A change's files are the union of its commits' files, and the 50-file limit applies to that union (with the files of earlier lives, as for a commit). The direct commits of an integration branch belong to no change: a pull request that names a release or `develop` branch (`main`, `master`, `develop`, `dev`, `staging`, `release/…`, `release-1.2`, `stable-2.x` and the like) as its source, or whose branch itself contains pull request merges or squash-merged pull requests (a `(#12)` suffix, `Merged PR 12: …`, `Pull request #12: …`), is a release and not one change, while the pull requests merged into that branch keep their own changes. Two limits keep a group from being one change: a pull request of more than 30 commits is not (a release branch merged into the mainline, a branch that was merged back and forth), and a ticket is not joined to other pull requests or commits when that would make a change of more than 50 files or 30 commits; its parts stay what they were. Mechanical commits never join a change, and with `--compare` each window is grouped on its own, so a pull request that straddles the split is cut in two. Without a squash suffix, a merge commit, or a ticket key, every change is one commit. `logicalChanges` in the report says what the grouping rests on (`by`: `pr`, `ticket`, `mixed` when both joined commits, or `commit` when none did), how many changes the window has (`count`, before the 50-file limit), and how many commits the largest holds (`largest`). A repository that merges in short branches or squashes every pull request loses the coupling that the commits of one change shared with each other, and a module's cohesion falls where its changes keep reaching into other modules, which is the point: one pull request is one decision about the design.
- **Indentation complexity** — the sum of indentation levels over the file's non-blank lines. A language-agnostic stand-in for nesting that tracks cyclomatic complexity well ([Tornhill, _Your Code as a Crime Scene_](https://pragprog.com/titles/atcrime2/your-code-as-a-crime-scene-second-edition/)).
- **Score** — `norm(revisions) × norm(weighted lines)`, where weighted lines are lines plus indentation levels and `norm(x) = ln(1+x) / ln(1+max)` over the repository. 0..1, relative to this repository: a 0.8 here says nothing about a 0.8 elsewhere.
- **Coupling degree** — `shared changes / mean(changes of both)`, where a change is a logical change (the previous item) and a file's `changes` counts the ones that touched it (`revisions` stays per commit, as the hotspot measure): a file edited in three commits of one pull request and in one other pull request has 2 changes and 4 revisions, and a pair that shares both has degree 1. Pairs need 3 shared changes and a degree of 0.3. Mechanical commits and changes touching more than 50 files (mass edits) are ignored for coupling.
- **Co-change probability** — `shared changes / changes of one file`: how likely a change to that file also changes its partner. The `analyze` terminal table shows it in both directions (`a → b`, `b → a`); `inspect` shows it for the focused file.
- **Hidden coupling** — every coupling in `analyze --json` has `imports`: `a→b` when file `a` imports file `b`, `b→a`, `both`, or `none` when neither does; `inspect` partners carry it seen from the inspected file (`file→partner`, `partner→file`, `both`, `none`). The terminal shows the same in an import column (`hidden` for `none`). An import counts when it is static (`import` and `export … from`, type-only included), a dynamic `import("…")` with a plain string, a `require("…")`, or the `import("…")` of a TypeScript type; importing a module also reaches what that module hands on: what it re-exports with `export … from`, the imports that occur inside an exported expression: the initializer of an exported variable, `export default <expression>`, `export { name }` of such a variable, `export =`, `module.exports = …`, or `exports.x = …` (`import { run } from "./b"; export const api = { run };`, `module.exports = { a: require("./a") }`). Only a name that references the import counts: not a plain property key, a member after the dot, or a JSX attribute name, and not a name used inside a function or class within the expression (`export const api = { go: () => run() }` does not hand on `run`). A `require()`, `import()`, or `new URL(…, import.meta.url)` still does wherever it is, so a route table, and an exported `() => import("./page")`, hand on their pages; what a class extends is evaluated with the class and hands on, its body does not. A top-level name stands for the modules its initializer loads or refers to (`const helper = require("./h").helper`) and what is assigned to it or to a member of it at the top level (`Form.Item = Item`), so exporting the name hands them on. What a class extends and what its decorators name hand on; an `implements` clause does not. An exported `import X = …` and an exported type alias that names an imported type hand on as well; an interface that extends one does not. So a file that imports a barrel imports what the barrel hands on. A `new URL("./worker.ts", import.meta.url)` is an import of that file. Relative specifiers resolve as TypeScript does (extension, `index` file, `.js` for `.ts` in TypeScript files; a specifier that stands for both a declaration file and a runtime file links both); the name of a workspace package (`name` in its `package.json`) resolves to the files its manifest maps `"."` to (else `main`, `module`, `types`, else its `index` file), whatever `--entry` says; a package that owns no files itself, such as a `backend/` folder above its sub-packages, resolves among the files below it, unless a package that owns files claims the same name. `none` is only reported when every module involved is accounted for: the two files, every file they import, and every file those hand on through must be readable and, where they are parsed, load nothing unresolved. Accounted for are universe files, Node built-ins (a bare name like `constants` only when no directory, and no code file without its extension, of the repository carries it), packages some `package.json` declares (or its `@types`), workspace packages, and tracked assets such as `.css` or `.json`. Otherwise `imports` is `null` (unknown): a file that is not TypeScript or JavaScript (`.ts .tsx .mts .cts .js .jsx .mjs .cjs`), does not parse, or the parser could not be loaded, and any import through a tsconfig `paths` alias, a `#` subpath import, a bundler alias or plugin scheme (`virtual:`), code outside the universe, an undeclared package or one whose name two manifests claim, component files (`.vue`, `.svelte`, `.astro`), or modules loaded by an expression (`import(name)`, `import.meta.glob()`, `require.context()`). A file whose strongest non-test co-change partner has no import and a probability of at least `thresholds.minHiddenProbability` gets a reason line.
- **Copy families** — files with largely the same content that keep changing together: the same change applied to each copy. Among the coupled pairs (not a file with its own test; contract files take part like code, and a ubiquitous file has no pairs), codeheat reads both files from the work tree and compares them as runs of five consecutive words: identifiers and keywords as they are, every string literal and number as one placeholder, and no whitespace, punctuation, or comments (`//`, `/* */`, `<!-- -->`, and `#` at the start of a line). The similarity is the Jaccard index of the two sets of runs, 0..1; a pair of at least `thresholds.minCopySimilarity` (0.5) makes both files copies of each other, and a family is a connected group of such pairs (files with fewer than 20 distinct runs are too small to compare). `copyFamilies` in `analyze --json` lists each family with its sorted `files`, the `similarity` range over all pairs of its members (the weakest can lie below 0.5: a chain A~~B~~C links A and C although they share little), `sharedChanges` (counted changes that touched at least two members) and `changesToAll` (counted changes that touched every member: fixes applied to all copies), most `changesToAll` first, except that families of test code only (`testOnly`: every member is test code, as for `file.test`, except that a contract file never is, even in a `spec` directory; the same rule holds wherever the report tells test code from the rest) come after the others, and `inspect --json` carries the family of each file as `copyFamily`. The terminal shows the first five that are not `testOnly` under "Copies", says how many test-only families it left out, and, in `inspect`, one line such as `changes with its 2 copies: …`. A family says the files change in lockstep; it does not call that a defect, since one adapter per entity or one config per environment is duplication on purpose. When every fix keeps landing in all copies, extracting the shared part is the design move to weigh.
- **Distant coupling** — a coupled pair that lies far apart in the design: its files are in different modules, or at least `thresholds.minLocalDistance` (3) directory hops apart within one module. Any pair with a test-code file is left out (a test belongs next to the code it checks, and a step file or helper next to nothing in particular), and so is a pair of two contract files. `distantCouplings` in `analyze --json` lists the best 50 by `score = strength × reach × hidden × evidence`: `strength` is the coupling degree; `reach` is `1 + log2(1 + hops)` between the two modules' directories for a pair across modules (at least 2.58, growing slowly so that deeply nested paths do not dominate), and for a pair within one module the file distance divided by the largest distance among the distant pairs (at most 1), because a module boundary is a design statement and directory steps only order what stays inside one module; `hidden` is 1.5 when no import links the files (`imports` is `none`) and 1 otherwise, an unknown relation included; `evidence` is `min(1, sharedCommits / 10)`, so a pair that met in three changes does not outrank one that met in eleven at a similar degree. Each entry also says `distance`, `crossesModule`, the `modules` of both files, `imports`, and `sharedCommits`. The terminal shows the first five under "Distant coupling" ahead of the plain coupling table, and `inspect` marks a distant partner with `distant: true`. A distant coupling says the change reaches across a boundary, not that the boundary is wrong: an app changes with the library it uses.
- **Module coupling and cliques** — `moduleCoupling` lists pairs of ranked modules (`minModuleCommits` counted changes, not test-only) that shared at least 3 counted changes, with `sharedCommits` and `share`, the share of the smaller module's counted changes that touched both: the data of a module coupling matrix, the 200 pairs with the largest share. A change that touched a contract file counts as a touch of the module the contract lives in. `cliques` lists the maximal groups of at least three ranked modules of which every pair shares at least `thresholds.minCliqueShare` (30%) of the smaller module's changes and at least 3 commits, and of which at least 3 changes touched every member, at most 50, those that changed together in the most changes first. A group in which fewer than 3 changes touched every member is searched for its sub-groups that pass (a search bounded at 1000 maximal groups of modules, searched by the best evidenced weakest link first, and at 500 intersections and 1000 distinct parts of one group; `cliquesPartial` is true when a bound was hit and a clique may be missing), and a clique inside another is dropped. Two cliques are variants of one unit of change only when their union is pairwise linked in the module pair graph (every pair shares enough changes and share, as for a clique) and they have at least `min(n − 1, ceil(0.8 n))` members in common, `n` being the size of the larger; of variants only the stronger stays (more changes touching every member, then more members, then path). Groups that share a core pair but whose other members never change together stay separate, so the list shows distinct units of change, not variants of one. Each has `sharedCommits` (commits that touched every member), `weakestShare`, and a one-sentence `reason`. Such modules are one unit of change cut by boundaries, or share an abstraction that is missing. The terminal shows the first three under "Change together (modules)".
- **Change radius and propagation cost** — the answer to "does the design contain change?". `changeRadius` counts, for each counted change, the modules it touched (a contract file counts for the module it lives in; test-only modules are left out, and a change that touched nothing else is not measured) and reports their `median` (lower median, a whole number), `p90` (nine in ten changes touched at most that many modules), `local` (the share that touched exactly one), and the number of measured `changes`. Each module's `radius` is the median number of modules, itself included, touched by the measured changes that touched it. It depends on what a module is (see Modules and cohesion): finer modules give a larger radius, and a repository with a single module always reads 1. `propagationCost` reads the co-change graph: the nodes are the files that are not test code and took part in at least 3 counted changes (`thresholds.minSharedCommits`; large changes are not counted, contract files are; a file with less history cannot be coupled at all), the edges are the reported couplings between two of them (3 shared changes and a degree of 0.3, `thresholds.minSharedCommits` and `minDegree`), and a file reaches another through a chain of at most `thresholds.propagationDepth` (3) couplings. The cost is the mean over the files of the share of the other files they reach, between 0 (no coupling) and 1 (everything reaches everything), with the number of `files` it ran over; a full closure would saturate near 1 on dense graphs. The cost shrinks as the number of regularly changing files grows, so it is a within-repository, over-time measure, not a score to compare between repositories of different size. Both are `null` without data (no counted change in a module; fewer than two files with enough changes). The terminal prints one sentence under the summary line ("Across 170 changes, a typical change touches 1 module; 9 in 10 touch at most 3 modules; 64% stay in one module.", without the clause on nine in ten below 10 measured changes), and `inspect` adds the radius to the module line. `propagationCost` stays in the JSON; the terminal does not show it. `--compare` does not give either a trend of its own; see Over time. `changeRadius.changes` can be lower than `window.couplingCommits`, since changes that touched only files that are dead today, or no module, are not measured.
- **Unstable interfaces** — TypeScript and JavaScript only. A file that at least `thresholds.minFanIn` (5) other files import directly (test code left out, a re-exporting barrel counting as the importer, not the files behind it), that changed in at least `thresholds.minInterfaceChanges` (5) logical changes (`FileStats.changes`: how often the interface was changed as a whole, not how many changes that took), and in more changes than the median of its dependents: every change to it risks all of them. `unstableInterfaces` lists at most 50, those that the most dependents changed along with first, each with `fanIn`, `changes`, `medianDependentChanges`, `changedDependents` (dependents that changed in a counted change that also changed the file), up to five `dependents` with the commits they share with it, and a `reason`. For the files that take part in a coupling, the dependency graph comes from the parser (the same one that decides hidden coupling); for every other file it comes from a text scan: import and `export … from` statements at the start of a line, and `require("…")` and `import("…")` calls with a plain string, comments ignored, resolved like hidden coupling resolves them, so an alias or a package that cannot be resolved adds no dependent. Fan-in is only as high as what resolves. The terminal shows the first five under "Unstable interfaces".
- **Dependency direction** — the Stable Dependencies Principle, from how often modules actually change rather than from how many depend on them. `dependencyDirection` lists the import edges between modules (TypeScript and JavaScript only, test code and test-only modules left out) that point from a module that rarely changes to one that changes often: the imported module has at least `minModuleCommits` counted changes and at least `thresholds.minVolatilityRatio` (2) times as many as the importing one, which may not have changed at all. Each edge has `importingFiles`, `changesTogether` (counted changes in which a file of the importing module changed together with a file of the imported module that it imports), `fromCommits`, `toCommits`, `ratio` (`toCommits / max(1, fromCommits)`), and a `reason`; at most 50, ranked by `log2(ratio) × log2(1 + changesTogether)` so that a framework that everything imports does not fill the list, and importing files and path break ties. It says where a change to one module reaches code that otherwise sits still, not that the import is wrong: an application depends on the framework it is built on.
- **Test pairs** — a file with its test is expected coupling; it is marked (`testPair`), never counted as a smell. A test has a suffix (`.test`, `.spec`, `_test`, `_spec`) and either sits beside its source (`a.ts` with `a.test.ts`, `a_test.go`, `a_spec.rb`) or lies below a mirrored test directory (`test`, `tests`, `__tests__`, `spec`, `specs`, `e2e`) whose mirror holds the source: the same path with that directory removed or replaced by `src` or `lib`. So `src/a/b.ts` pairs with `test/a/b.test.ts` and `tests/a/b.spec.ts`, `lib/x.ts` with `__tests__/x.test.ts`, `packages/p/src/y.ts` with `packages/p/test/y.test.ts`, and `src/x.ts` with `src/__tests__/x.test.ts`. Nothing else pairs: a similar name elsewhere in the tree, or a helper, step file (`login.steps.ts`), or mock below a test directory, is test code (`file.test`) but no one's test; a test below a `fixtures` or `__fixtures__` directory is never mirrored to a source; and the support directories (`testing`, `test-utils`, `test-helpers`, `__mocks__`, `mocks`, `__snapshots__`) add no pairing of their own: their files are test code, and one of them can still be the source or the suffixed test of a pair beside its partner (`src/testing/a.ts` with `src/testing/a.test.ts`).
- **Breadth and hubs** — breadth is the number of co-changed files: distinct other files that shared a counted change (at most 50 files) with this one, however rarely. A hub is a file with at least 5 changes (`changes`, not commits), not test code (a test suffix, or a `test`, `tests`, `__tests__`, `spec`, `specs`, `e2e`, `fixtures`, `__fixtures__`, `testing`, `test-utils`, `test-helpers`, `__mocks__`, `mocks`, or `__snapshots__` directory, as for `file.test`), with a breadth of at least 10 among the widest 5% of such files (ties included); it gets a reason line even when no single pair is coupled strongly enough to report, as with barrels.
- **Modules and cohesion** — a module is a package (a directory below the root with a tracked manifest, even one an ignore rule matches: `package.json`, `go.mod`, `Cargo.toml`, `pyproject.toml`, `pom.xml`, `build.gradle`, `build.gradle.kts`, or `*.csproj`; a file belongs to its nearest package) or, outside packages, a directory, cut where the files first split into two or more directories (when no depth splits them, at the first level: `scripts/release.ts` and `scripts/lib/util.ts` are one module `scripts`). A repository that yields a single module is split by directory instead, and so is a module that holds more than 70% of the files and at least 20 of them (a lone package beside a small `scripts/`, or `src/` beside a small `test/`), again while a part holds more than 70%: the directory rule then cuts it into modules inside it. A smaller repository keeps its modules. A package is never split while other packages with files in the analysis exist, however large it is, because its manifest is a boundary someone declared (a package of test code alone, such as a fixture's manifest, does not count). A split package becomes directory modules, still importable by its name; the entry file named in its manifest usually forms a module of its own, so the leakage and depth of the split code are `null`. A module's cohesion is the share of its counted changes (at most 50 files) that touched no other module; `partners` lists the modules the rest touched. Modules are ranked only when they have at least `max(5, 1% of the commits counted for coupling)` counted changes (`thresholds.minModuleCommits`) and are not test-only (`testOnly`: every file is test code, by a test suffix or a `test`, `tests`, `__tests__`, `spec`, `specs`, `e2e`, `fixtures`, `__fixtures__`, `testing`, `test-utils`, `test-helpers`, `__mocks__`, `mocks`, or `__snapshots__` directory). `modules` lists the ranked ones first, least cohesive first. A coupling between files of different modules is marked `crossesModule`, neutrally: an app legitimately changes with the library it uses.
- **Territories** — a tree of non-overlapping areas of the code, finer the higher the detail, to find your way in a repository you do not know (`territories` in `analyze --json`, a node per area; `modules` is unchanged and does not depend on it). Detail 1 is the first cut: the repository's top-level folders (a chain of single subfolders counts as one step, and a package's directory is never skipped over); a folder with fewer than 3 files stays loose in an `other` node with the files directly in its directory, unless it holds at least 1% of all heat (`MIN_VISIBLE_HEAT`, a policy constant), when it is a part of its own like a larger folder. Below the first cut, a directory with a single child folder (a package with its `src` and some files beside it) splits into that folder's children, the loose files of each directory a node of their own named after it. A territory splits into its child folders when it is too big, with more than 40% of the code files or more than `min(150, max(50, files / 4))` files and at least `max(8, thresholds.minModuleCommits)` counted changes, or when its folders change independently: at least 70% of the counted changes touching it stay inside one folder, over at least that many changes, and two folders each have 3 changes or more. Folders whose changes largely coincide stay together as a `group` (the Jaccard index of their changes is at least 0.4 over at least 5 shared changes, at most 3 folders), and at most 8 children open at once, the ones with the most heat first (then the most changes, then the most files), and the rest wait in an `other` bucket ("9 smaller folders in packages") that opens at a finer detail. The splits are taken in order of value, big, busy, and hot territories first, independence a bonus, and spread over details 2 to 6 so that the count grows steadily; the tree stops at `max(60, files / 60)` territories. `recommended` is the finest detail with at most 25 territories (`other` nodes and test-only territories never count) in which no bucket or node of loose files holds a folder that is hotter than the coolest territory opened beside it and holds at least 1% of all heat (`MIN_VISIBLE_HEAT`; below that the comparison is noise; a folder with too few files to be a territory counts like any other); when every detail with at most 25 territories hides such a folder, the finest of them, and its bucket is reported as it is; within a detail they sort after the real territories. Test code belongs to the territory of the code it tests: a test that pairs with a source file (see Test pairs) (a test class `FooTest`, `FooTests`, `FooIT`, or `FooSpec` pairs with `Foo`, and `src/test` mirrors `src/main` in a Maven or Gradle layout) or lies below a test directory beside code (for a top-level `test/`, beside `src/`, `lib/`, or `main/`; otherwise beside the directory's parent) counts for that territory's files, changes, and heat; when the children of a territory are ranked for opening, test code placed in a directory heats only a folder that contains that directory, never the cold folders beside a hot one. When the code a test directory belongs to is split into several territories, its tests get a `tests` territory of their own beside them, so they do not inflate one of the parts; test code with no code beside it is a `tests` territory of its own as well, and when one package holds every file it is the root. A node that splits says why in `splitReason`: how many code files, and whether its parts still change together, change independently, or mostly stay inside one part, and which folders stay together. `description` says what a territory is in one line that is safe to print (no control characters, at most 160 characters): the `description` of its manifest (`package.json`; the `[package]`, `[project]`, or `[tool.poetry]` table of `Cargo.toml` and `pyproject.toml`; the project's own top-level `<description>` of `pom.xml`; of a `Cargo.toml`, `pyproject.toml`, or `pom.xml` the first 65,536 characters are read), else the first sentence of its README (the first 2 KiB of the first paragraph of prose, past headings, badges, links, directives, and code; not read when the work tree holds a link instead of the file), else `main files: a, b, c`, its most changed files; a manifest or README over 256 KiB is not read at all, and `other` and `tests` nodes say what they are first. `heatShare` is the territory's share of the repository's heat, the sum of `changes × (loc + complexity)` over its files, and every file names its finest territory in `territory`. Each territory carries its design fit in `fit`, measured once with the module measures' rules over the territories visible at the detail closest to the recommended one (`fit.detail`): `containment`, the share of the changes touching it that touch no other territory (the cohesion of a territory), the `radius` of those changes, the `partner` territory they most often reach into, the coupled file pairs that cross its boundary (`distantPairs`, and `hiddenPairs` that no import links), the `cliques` of territories it changes with as one unit, its `erosion` over the series, `chronicFiles`, `acuteFiles`, and the `chronicShare` of its heat, and its `fixDensity`; test-only territories and the root have none to report. The terminal prints how many territories the recommended detail has.
- **Territory coupling and territory cliques** — `territoryCoupling` and `territoryCliques` in `analyze --json` say which territories change together, at the recommended detail only (the data of a territory matrix). `territoryCoupling` lists each pair of the `maxCoupledTerritories` (24) hottest real territories (package, folder, or group; never a bucket or test code) that share at least 3 counted changes, once, lower id first, strongest first, with `sharedChanges` (counted changes that touched both, by the same code as a territory's `partner`, which is so among its pairs when the partner is among those hottest too, over territories with at least `minModuleCommits` changes), `distantPairs` (coupled file pairs between the two, the rule of `fit.distantPairs`), and `hiddenPairs` (of those, the pairs no import links). A pair that is missing shares too few changes or involves a territory below the ranking: it says "not enough evidence", not "independent". `territoryCliques` lists, at most 50, the groups of three or more territories that change as one unit (the rule of a clique over territories: every pair shares at least `minCliqueShare` of the smaller one's changes and at least 3 changes, and at least 3 changes touched every member), with `territories` (ids), `sharedChanges`, `weakestShare`, `heatShare`, and `codeHeatShare`, the numbers an entry point of kind `clique` is scored on. `--limit` does not cut either. Both are additive (schema version 1) and will move under `coupling` in v2.
- **Where to start (entry points of the report)** — `entryPoints` in `analyze --json` and the first section of the terminal view after the summary: at most ten places where the design fails to hold up to the way the code changes, each with a `kind`, the territories and files it concerns, its `evidence`, a one-sentence `verdict`, and a `designMove`. The six kinds are in the table below. `inspect` names the entry points a file belongs to: an entry that names files concerns exactly those, one that names none concerns every file in its territories. These are not the module entry points of the next item.

The heat share of a file set is the share of all the production code's heat (the heat of a file is `changes × (loc + complexity)`; a test file holds none, in the total too: tests are change effort but not design) that its files hold, so every score is a share of the production code's heat at stake times how strong the weakness is, and scores of different kinds compare as the share of change effort at stake. A territory that is a bucket of smaller folders, loose files, or test-only code never qualifies. A territory that qualifies as both `boundary` and `hotspot` is one entry whose `kind`, `verdict`, `designMove`, and `score` are those of the stronger finding (a boundary on a tie) and whose `findings` list both, the stronger first. Each kind keeps its `maxEntriesPerKind` best entries. The best entry of each kind is always listed, whatever its score, as long as it passes the gates of its kind above (on a large repository the file-level kinds never reach half a percent of the change effort, and would vanish); the rest fill the list by score up to `maxEntries`, and every one of them scores at least `minEntryScore` (0.005: half a percent of the change effort). A file-level entry (`copies`, `hub`, `coupling`) whose files a higher ranked entry already names all of is left out. All the gates named above are in `thresholds`. `inspect` gives the territory of a file and the one it changes with most, with their `fit`, for the files that are in no entry.

- **Entry points and leakage** — a module's entry points are the files that make up its public interface: for a package, the files its `package.json` names in `exports` (strings and nested conditions), `main`, `module`, and `types`, counting only JavaScript and TypeScript files and no `*.config.*` files (a `*` in a target matches any files; a target without extension finds the file with that name; a target in `dist/` or `build/` stands for the same-stem source under the package's `src/` or root, when one exists), plus `index.{ts,tsx,mts,cts,js,jsx,mjs,cjs}`, `mod.rs`, `lib.rs`, and `__init__.py` at the module root or its `src/`; a directory module uses the conventional files only (the pieces of a package that was split also take the files its `package.json` names that lie in them). `--entry` replaces all of that with the files its globs match. `interfaceCommits` counts the module's counted changes that touched an entry point, `implementationCommits` those that touched any other file of the module that is not test code (a test suffix, or a `test`, `tests`, `__tests__`, `spec`, `specs`, `e2e`, `fixtures`, `__fixtures__`, `testing`, `test-utils`, `test-helpers`, `__mocks__`, `mocks`, or `__snapshots__` directory). Leakage is the share of the implementation changes that also touched an entry point; it is `null` without entry points or implementation changes. A high leakage means changes inside the module keep changing its public API, a sign of a shallow or leaky module. A module is flagged `leakyInterface` at a leakage of at least 50% over at least 5 implementation changes (`thresholds.minLeakage`, `thresholds.minImplementationCommits`) unless it is test-only. Its entry points that changed in at least one commit that also changed the implementation get a reason line, so a root `index.ts` that only re-exports `src/index.ts` stays unmarked. The terminal lists the first flagged modules in the order of `modules`. That order is by cohesion, so look for `leakyInterface` in the JSON and use `--limit 0` to see all modules. Read leakage with two limits in mind: behind an `export *` barrel the public API can grow in implementation files, so a low leakage does not prove a stable API; and an entry file that holds most of a module's code inflates the leakage, because every change to the module touches it.
- **Module depth** — Ousterhout's depth: how much implementation sits behind how much interface. `Module.depth` is `{ exports, implementationLines, linesPerExport }`. `exports` is the number of distinct names the module's entry points export (a name that several entry points export counts once): declarations, `export { a as b }`, `export { x } from "…"`, `export * as ns from "…"`, a type like a value, `default` as one name, and, through `export * from "./x"`, every name that file exports, followed transitively within the module. As in ECMAScript, a file's own export wins over `export *`, `export *` does not forward `default`, and a name that two `export *` sources export as different bindings is exported by neither (the same binding reached twice counts once). A name taken by a named re-export counts even when its source is out of sight, such as an excluded or missing file or an asset. `implementationLines` is the sum of the non-blank lines (`loc`) of the module's files that are neither entry points, test code, nor tool configuration (`eslint.config.mjs`, `vitest.config.ts`, …), and `linesPerExport` is their quotient, rounded to 4 decimals. A low value is a shallow module, a wide interface with little behind it; a high one is deep. The terminal's "Shallowest modules" lists the five ranked modules (see cohesion) with the fewest lines per export (the section is left out when none has a depth), and `inspect` states the depth of the module of each file. `depth` is measured on the code as it is now, whatever the window, and is `null` when it cannot be told exactly: the module has no entry points, one of them is not TypeScript or JavaScript or does not parse, the parser could not be loaded, an entry point exports without ES syntax (`export =`, `module.exports`, `exports.x`), an `export * from` names a package, an unresolved specifier, a specifier that resolves to several files, or a file of another module, two bindings of a name cannot be told apart, it exports nothing, or no other file is left to count as implementation (all code sits in the entry points, in tests, or in configuration files). Read it with two limits in mind: it measures size, not complexity, so a module that keeps its code in one big file or in many small ones reads differently; and an entry file that holds code of its own counts that code on neither side. A tiny module with a handful of exports reads as shallow, which is why the terminal ranks only modules with enough commits.
- **Trends** — `--compare 3m` reads six months of history once and splits it at the start of the latest three months. Both halves are measured over the same files (those that exist now) and with the same fixed limits, such as the 50-file cap on counted changes; the module floor `thresholds.minModuleCommits` grows with the window, and the report's `thresholds` are the latest window's. Every other field of the report describes the latest window, exactly as `--since 3m` would. A file's `trend.scoreDelta` is its score now minus its score in the previous window (`trend.previousScore`, from `trend.previousRevisions` revisions), each normalized within its own window, so it shows a shift in standing among the files, not a change in raw revisions. `trend.newlyActive` is true for a file with no revisions in the previous window: its delta is then just its score, so it appeared rather than warmed up. Only the file that exists today has revisions in either window, so a path recreated after the previous window's changes is newly active, whatever the file deleted at it did before. `file.test` marks test code; rank warming only among files where `test` and `newlyActive` are false, as the terminal does. A module's `trend.cohesionDelta` is the change in cohesion, positive when the module became more self-contained; it is set only for a module with at least `thresholds.minModuleCommits` counted changes in both windows. A trend is `null` without `--compare`, for files when either window has no real commits (none that is not mechanical), and for modules that do not reach that floor in both windows. `comparison` names the previous window, counts its commits (`previousCommits`) and those that are not mechanical (`previousRealCommits`; 0 means nothing to compare, not that nothing changed: a window that holds only mechanical commits, such as one reformat, has no activity to compare against), and sets `previousTruncated` when the window reaches back past the oldest commit of the repository or of a shallow clone. The terminal lists the five source files that got hotter most, the three highest-ranked newly active source files, and the five modules whose cohesion moved most, and says so when a window has no real commits (no commits, or only mechanical ones) or is cut off. The treemap draws newly active files and files without data with a diagonal hatch, so they never pass for unchanged; a merged tile takes the color of its largest move in either direction.

The report states every threshold under `thresholds`, and the JSON contract is versioned by `schemaVersion`: new fields may appear, but a field is never renamed or removed without a new version.

- **Over time: erosion, chronic and acute hotspots, fix density** — the answer to "is the design holding?". `series` is the last 24 months or more of history cut into consecutive windows of about a quarter of a year (91 days) each, oldest first, at most 12, equal in length, the last ending at `window.until` (`Report.series`, starting at `Report.seriesSince`). The series covers at least the last 24 months whatever `--since` or `--compare` say, or the whole history if that is shorter (it starts at the oldest commit), and a longer analysis window extends it, so it can start before `window.since`; the measures of the window itself (hotspots, couplings, modules, radius, …) keep using `window`. A span shorter than about 4.5 months (20 weeks, one and a half quarters) is not cut at all, and the windows grow longer than a quarter once the span covers more than three years (36 months, 12 windows). They come from the one read of the history, which starts at the series start: a window groups, couples, and counts only the commits that landed in it, so a pull request across two windows is split between them, and the slices are classified over the series span (reverts, re-lands, and duplicates are paired inside it, and the merges that group commits into pull requests are read from its start), while the numbers of the analysis window itself are classified over the window span, as if it were read alone, so they equal those of a run that reads only the window; a commit can therefore be mechanical in a slice and not in the window, or the other way. Each reports its `changeRadius` and `propagationCost` and whether it is **active**: at least `minWindowChanges` (10) counted changes. Nothing below counts an inactive window. `erosion` says whether changes keep staying in one module: A robust line (Theil–Sen: the median of the slopes between every two active windows, and the median intercept, so one odd window cannot turn it) is fitted through a measure over the active windows and read at the first and last of them (`TrendLine`: `from`, `to`, `slope` per window; the values are the line's own, not held to 0–100 %). The repository's `Report.erosion` fits the share of changes that stay in one module (`changeRadius.local`). The verdict is `eroding` only when the line fell, and `improving` only when it rose, by at least `minErosionShift` (10 points) **and** at least `minErosionSigmas` (2) standard errors of that shift, otherwise `holding`; `unknown` with fewer than `minTrendWindows` (3) active windows. The same verdict must also follow from the active windows without the first and the last (a line fitted through the others, and the same gate), which needs at least `minVerdictWindows` (5) active windows: with three or four the verdict is `holding`, so one odd window at either end cannot decide it. The standard error is that of a weighted least-squares line through the windows' shares, whose variance is binomial, `p(1-p)/changes` with `p` the pooled share (not below 5 % or above 95 %), widened by 15 % for the Theil–Sen estimator and for changes that burst together; a flat design reads `holding` in more than 95 % of simulated cases from 60 changes a year up, and one odd window does not decide. The verdict describes the **active period**: inactive windows are left out wherever they lie, so they can neither cause nor hide a verdict, and a quiet end of the series is reported separately as `Erosion.inactiveSince`, the start of the run of inactive windows that ends it (null when the last window is active). The propagation cost gets a line for context, not for the verdict. A module's `Module.erosion` fits its cohesion over the windows in which it had at least `max(minWindowChanges, minModuleCommitsFor(the window's counted changes))` counted changes, with the same gate (`verdict`), the cohesion of every window, and `recent` (evidence in one of the last two windows). **Hotspots by age:** A file is **hot** in a window when it has revisions there and its score, computed from the window's revisions, is among the best `hotTopShare` (a tenth, rounded up, ties included) of the non-test files with revisions in the window. The windows that count for a file are the active ones from the first window in which it has a revision (all git shows of when it appeared). It is **chronic** when at least `minTrendWindows` (3) of them lie before the last two windows and it was hot in at least half of those and in at least half of all that count for it (the last two included): a design problem rather than a feature being built, and not one that cooled long ago. The last two windows do not count towards chronic, so a series needs at least five windows (about 15 months of history; the default 24 months give eight) before any file can be chronic. It is **acute** when it was hot in both of the last two windows and in fewer than half of the windows that count for it before them, with an active window before them to compare with: current work; a file hot in every window of a series too short to call it chronic is neither. A file that is neither has no `heat`, and neither has test code. **Fix density:** A subject is a fix when it has the `fix`, `hotfix`, `bugfix`, or `revert` type of Conventional Commits (`fix(scope)!: …`), starts with `Revert "`, or has `fix`, `fixes`, `fixed`, `fixing`, `bug`, `bugfix`, or `hotfix` as its first word, unless `bug` is followed by a ticket number (`Bug 1234 - …`, `BUG-12`, `bug #7`), which names a ticket, or has a lowercase scope, a colon, and `fix`, `fixes`, or `fixed` after it (`compiler: fix crash`, but not under a Conventional Commits type such as `feat:`); a change of several commits is a fix when more than half of them are. A module also counts the fixes that **span** modules: those that also touched another module that is not test-only, which mark the boundary as fragile. It is **known** when at least `minConventionShare` (5 %) of the changes have a fix subject (by any of the rules above, so a team that writes free text and often starts with "Fix" gets a share) or another Conventional Commits type (`feat`, `docs`, `chore`, …); below it the subjects say too little, and the fix density is unknown, never 0. These rules are fixed in the engine; there is no flag to change them. The terminal's "Over time (since …)" section, headed with where the series starts, prints the verdict with its numbers (and "quiet since …" for a series that ends quiet), the three modules whose cohesion fell most while still changing (only those whose module verdict is `eroding`), the number of chronic and acute hotspots with the three highest-ranked chronic ones, and the fixes; `inspect` marks a chronic or acute file. The series always covers at least 24 months (eight windows), so the default run can classify chronic files and judge a trend; a longer `--since`, or an older history, gives up to 12 windows.

## Known limits

- Hidden coupling reads imports, not other ties. Where imports are not resolved (aliases, code outside the analyzed scope or the universe), the pair is unknown (`null`) rather than hidden, so a repository that relies on aliases gets fewer answers, not wrong ones. Files in other languages than TypeScript and JavaScript report `imports: null`, and a module whose entry points are in another language has no `depth`.
- Unstable interfaces and dependency direction read every non-test TypeScript and JavaScript file once, as text (the files of coupled pairs are read by the parser). The scan tells strings, template literals, regular expression literals after an operator or bracket, and comments apart in one pass, so a glob in a string such as `"src/*.ts"` opens no comment. What it still gets wrong: a quote or backtick inside a regular expression the pass does not recognise (after a keyword other than an operator, say) or inside JSX text can open a literal that runs to the end of its line, or, for a backtick, to the next one; an import statement inside a template literal or a block comment that starts a line looks real; a `${…}` holding a template literal of its own can shift where later literals begin; an import that does not start its line, a re-export through an exported expression, and a module named by an expression are not seen; what it cannot resolve to a universe file is no dependency. The scan adds a few percent to the time of an analysis of a large repository.
- Test code is told by name, not by purpose: a production package or folder that happens to be named `testing`, `test-utils`, `test-helpers`, `mocks`, `__mocks__`, or `__snapshots__` (a published `testing` entry point of a library, say) counts as test code, so its files are no hubs, hotspots that warm, or distant couplings, and a module made only of such files is test-only. `--exclude` can only remove files from the analysis, not reclassify them; an option to override the rule is not there yet.
- Contract files are partners, not subjects: `inspect` shows code files, so `inspect api/orders.tsp` says `"api/orders.tsp" is a contract file; inspect the code that changes with it` (exit code 4 when nothing else matched; `contractFiles` in `--json`), and the contract appears among the partners of the code that follows it. The list of contract files is fixed (no flag adds a file to it); `--exclude` removes one, and a file in another schema language is analyzed as code only when `--include` names it.
- The code parser is a native module (`oxc-parser`, the one runtime dependency of the package). Where its binary cannot load, codeheat says so on stderr, reports `imports: null` and no module `depth`, and still runs everything else.
- Copy families only compare files that already change together, read from the work tree as it is now (not from the history), and read comments and strings by a few language-agnostic markers (`//`, `/* */`, `<!-- -->`, `#` at the start of a line; quotes, double quotes, and backticks), not by a grammar. What that gets wrong shifts a similarity, never fails the analysis: `--` comments (SQL, Lua, Haskell, Elm) and Haskell `{- -}` blocks are read as code, a Python docstring (`"""`) spans lines but a quote ends a string at the end of its line, so the prose of its later lines counts as words, `//` integer division in Python starts a comment that swallows the rest of its line, an unpaired backtick (inside a regular expression, say) starts a string that runs to the next backtick or the end of the file, and a `/*` or a quote inside a regular expression opens a comment or a string the language does not see. Copies that never changed together, copies that drifted below 0.5, and copies in files too small to compare are not found.
- Indentation is a proxy. Unusual formatting distorts it; minified files are excluded for that reason.
- Shallow clones lack history; codeheat warns and ignores the boundary commit. Run `git fetch --unshallow` for full results.
- git gives up on rename detection in very large commits (`diff.renameLimit`) and does not see a move that changes more than half of a file. Such a move is a deletion plus a new file, so edits from before it stay with neither path.
- Merge commits are not read (`--no-merges`), so a deletion or a creation made only inside one is not seen: a path deleted only inside a merge and created again later still inherits the old file's history. A file added only inside a merge hides older history of its name only when that file is later deleted and the path created again, until a rename away from that name is seen.
- Whitespace-only commits are found with `git diff -w`, so a change that only adds or removes a space inside a string literal counts as whitespace. `-b` would stop catching formatter runs that insert spaces, the main noise source. Languages where indentation is syntax are excluded (see Mechanical commits).
- A shallow clone can turn a re-land into a duplicate: when the older copy of a patch is cut off, the later copy has no ancestor to show it applies on top of it.
- Each run reads the history again; there is no cache yet.
